# O2OA AI 网关能力扩展分析（rerank / 工具调用 / MCP / 多模态 / OCR / Agent Harness）

> 日期：2026-09-19　｜　分析对象：`D:\O2OA\gateway\o2_agent_gateway.py` + 官方 llama.cpp standalone 后端

## 1. 逐项分析

### 1.1 `/v1/rerank` —— ⚠️ 能做，但**做了收益接近零**（当前架构下）

**技术可行性**：完全可行。三步：
```bat
:: 启动参数加 --rerank（并在 embed 进程上）
llama-server.exe -m <bge-reranker.gguf> --rerank --pooling rank -ngl 999 --port 8090
```
```json
// config.json 加一行
"rerank_base": "http://127.0.0.1:8090"
```
```python
# 网关加函数，在 search_chunks 之后做二段精排
def rerank(query, docs): ...   # POST /v1/rerank
```

**但为什么说收益接近零**——这是需要澄清的认知偏差：

当前 RAG 检索是**纯向量暴力检索**（`search_chunks` 算余弦相似度，取 top_k=6）。
在小规模知识库（几十~几百文档，chunk 数几千）下：
- 向量 top-6 召回率已经很高；
- rerank 的价值在于**大规模候选集**（top-50 → top-5）的精排，
  以及**提升排序质量**（让最相关的排第一）。

而 O2OA 智能助手的使用形态是**单轮问答 + 6 条上下文**，用户感受不到 top-6 内部的顺序差异。

**真正值得做的替代方案（性价比高得多）**：

| 方案 | 成本 | 收益 |
|---|---|---|
| ① 混合检索（BM25 关键词 + 向量，RRF 融合） | 中 | **高**——专有名词/编号（"2024-08 号文件"）向量检索经常漏，BM25 能补 |
| ② 查询改写（query expansion，用 4B 模型生成 2-3 个变体再检索） | 低 | **中高**——口语化提问 → 文档术语的鸿沟，比 rerank 更治本 |
| ③ 加 rerank | 中（多一个常驻进程 + 400MB 模型） | **低**（当前规模下） |

**我的建议**：**先做 ②，验证效果后再决定是否做 ①。rerank 排到最后。**
如果一定要做 rerank，请同时把 `rag_top_k` 从 6 提到 20，形成"粗排 20 → 精排 6"的链路，否则 rerank 没有作用空间。

### 1.2 Tool Calling —— ✅ **后端已就绪，网关已实现，真正缺的是"好用的工具"**

**后端**：`supports_tool_calls=true`、`supports_parallel_tool_calls=true` ✅ **零改造成本**。

**网关**：`from_mcp_loop()`（line 440-489）**已经是一个完整的函数调用循环**：
```python
for turn in range(CFG["max_turns"]):          # 最多 5 轮
    r = post(f"{bionic_base}/v1/chat/completions", ..., tools=tools)
    calls = m.get("tool_calls") or []
    if not calls: break
    for call in calls: exec_tool(target, fargs)   # 自动执行
```

**所以 tool calling 不需要"新增能力"，它已经在跑。** 问题在别处：

**真实瓶颈（按严重度排序）**：

1. ★ **工具定义来自 O2OA 的 `McpConfig`，用户得手工填 URL/headers/body 模板**。
   这不是"网关能力不足"，是"没有开箱可用的工具"。
   → **对策：在网关内置一批"本地原生工具"**，绕过 O2OA 的 MCP 配置界面：

   | 内置工具 | 实现 | 价值 |
   |---|---|---|
   | `kb_search(query)` | 直接调本地 `search_chunks` | 让模型自主决定何时检索知识库（比强制 RAG 更准） |
   | `get_current_time()` | 系统时间 | **4B 模型必错项**，必加 |
   | `calc(expr)` | 安全的表达式求值 | 模型算术不可靠 |
   | `search_org(keyword)` | 调 O2OA REST 查组织架构 | 办公场景高频 |
   | `list_my_todo()` | 调 O2OA 待办 REST | 办公场景高频 |
   | `query_data(table, filter)` | 调 O2OA 数据中心 REST | 打通数据中心（低代码核心） |

   实现方式：在 `from_mcp_loop()` 里把 `tools_cfg` 与内置工具清单合并，`exec_tool()` 里先查内置表。
   **改动量约 80 行，收益是"从 0 到 1"级别的。**

2. **`reasoning_effort: "none"` 被硬编码**（line 465、321）。
   4B 模型关掉思考链后，工具选择的准确率会明显下降。
   → 建议：MCP 循环里**保留思考**（或加开关），最终回答再用 `none`。

3. **`max_turns=5` 偏少**，复杂任务会截断。建议提到 8-10，并加超时保护。

### 1.3 MCP —— ✅ 已实现，缺的是**传输方式与工具生态**

**现状**：网关只实现了 **HTTP 型 MCP**（`httpOption: {url, method, headers, body}` + `${参数}` 占位符替换，line 240-267）。

**三个层面的缺口**：

| 缺什么 | 说明 | 建议 |
|---|---|---|
| **stdio 型 MCP** | 官方 MCP 生态绝大多数 server 是 stdio（npx/python 起的子进程） | ⚠️ 可做但要谨慎：需子进程管理 + 生命周期 + 崩溃重启。**建议放在独立进程而非网关内** |
| **MCP 协议版本** | O2OA 的 `McpConfig` 是**自定义简化格式**，**不是标准 MCP JSON-RPC** | 不要试图兼容标准 MCP 协议去迎合 O2OA；O2OA 给什么格式就翻什么格式 |
| **工具质量** | 手工配 HTTP 接口，等于让用户写胶水 | 见 1.2 的"内置工具"对策 |

**关键判断**：O2OA 的 MCP 是**披着 MCP 名字的"HTTP 接口配置器"**。所以：
- ❌ 不要为了"支持标准 MCP"去重写协议栈——**收益为 0**，因为 O2OA 前端不会发标准 MCP 消息。
- ✅ 正确的做法是**把标准 MCP server 的能力，通过"内置工具适配器"暴露给模型**。即：网关内部跑一个标准 MCP client，把 MCP server 的 tools/list 转成我们自己的 tool 定义，注入 `from_mcp_loop()`。

这样既拿到了整个 MCP 生态（filesystem / fetch / git / sqlite / 各类 SaaS），又不用改 O2OA 一行代码，也绕开了它那个简化格式。
**这是本项最高价值的落地方向。**

### 1.4 多模态 —— ✅ **成本极低（一个启动参数），但需要先打通"图片怎么进来"**

**后端成本几乎为零**：mmproj 文件已在（675MB），只需在启动命令加 `--mmproj`：
```bat
llama-server.exe -m Qwen3.5-4B-Q8_0.gguf --mmproj mmproj-Qwen3.5-4B-BF16.gguf ...
```
当前 `start_llama.bat:44-48` **已经写了这个分支**（`if exist "%MMPROJ%"`），
但**实测 `/props` 显示 `vision:false`** —— 说明当前运行的进程不是用这个脚本起的（是手工后台起的，漏了 `--mmproj`）。
→ **对策：重启一次走 `start_llama.bat` 即可验证。**

**真正的难点在链路，不在模型**：

O2OA 的 `referenceIdList` 里放的是**附件 ID**（O2OA 的 `File` 实体），不是图片二进制。
网关要支持多模态，必须补两段：

```
① 网关调 O2OA REST 下载附件内容（需要附件读取权限 + 网关持有管理员 token）
② 判断 MIME：
   - image/* → 转 base64 塞进 content 数组 [{"type":"image_url","image_url":{"url":"data:image/png;base64,..."}}]
   - 其它    → 走现有 Tika/文本提取路径（网关当前对非图片没有 Tika，需补）
③ 组装 OpenAI 多模态 messages 格式
```

**注意 template 限制**（已知坑的延伸）：Qwen3.5 模板里
```
{%- if is_system_content %}{{ raise_exception('System message cannot contain images.') }}
```
→ **图片只能放在 user 消息里，且我们已有的"RAG 上下文合并进首条 system"逻辑要继续保持**。两者不冲突，但改造 messages 组装时必须注意别把图片塞进 system。

**风险评估**：4B 的 VLM 能力有限（能描述图片大意，读表格/小字会明显吃力）。**如果是文档理解场景，OCR 反而是更可靠的路**（见 1.5）。

### 1.5 OCR —— ❌ **llama-server 不提供，必须引入独立引擎**

**这是用户 5 项里唯一"确实完全没有"的能力**，需要引进外部组件。

**必须先搞清楚需求分型**（决定方案，成本差 10 倍）：

| 场景 | 推荐方案 | 说明 |
|---|---|---|
| **A. 扫描件/图片 → 文字**（最常见） | **RapidOCR (ONNX)** | 中文效果好、纯 CPU 可跑、无需 ROCm、pip 装完即用、模型约 15MB。**首选** |
| B. 复杂版面（表格/多栏/公式） | **PaddleOCR PP-StructureV3** 或 **MinerU** | 强，但依赖重、CPU 慢；有 GPU 版但本机 ROCm 生态不支持 |
| C. 手写体 | 无好离线方案 | 建议放弃，或手写场景改走多模态 VLM |
| D. 已存在文字层的 PDF | **不需要 OCR**——直接文本提取 | 当前 O2OA `o2AiFileList` 含 pdf，但要确认是否走了文字层提取 |

**落地方案（推荐 A）**：
```
新进程：ocr-service (FastAPI, :8091)
  ├─ POST /ocr  {image_b64 | pdf_b64} → {text, blocks[]}
  └─ 引擎：RapidOCR ONNX（CPU，不占 VRAM）
网关接入：
  ① RAG 索引时：先 OCR 再分块入库（替代当前纯文本假设）
  ② 对话时：referenceIdList 里的图片 → OCR → 文本 → 注入上下文
```

**为什么用独立进程而不是塞进网关**：
- OCR 是 CPU 密集、秒级耗时，塞进网关会阻塞事件循环（网关当前用 `anyio.to_thread` 桥接同步流，已接近极限）；
- 独立进程可单独重启、可换引擎、可加缓存。

**与多模态的分工建议**：
- **图片里有字** → OCR（准确、便宜、可检索）
- **图片是场景/照片** → VLM（理解语义）
- 两者可组合：OCR 拿文字 + VLM 描述画面。

### 1.6 Agent Harness（deepseek CLI / OpenClaw 类）—— ⚠️ **强烈建议独立旁路，不要并入网关**

**先说一个容易误判的点**：O2OA 开源版**没有** Agent 能力（无 ReAct 循环、无规划、无多步执行、无沙箱）。
网关现在的 `from_mcp_loop()` 是**最简 tool-calling 循环**，不是 Agent。
所以"加 Harness 能力"确实能补上一个大空缺——**但补在哪里是关键决策**。

**我明确反对把 Harness 塞进 `o2_agent_gateway.py`**，理由：

| 冲突点 | 说明 |
|---|---|
| **超时模型冲突** | O2OA 的 SSE `READ_TIMEOUT=0`（永不超时），Harness 任务却要跑几分钟到几十分钟 |
| **交互模型冲突** | 网关是"请求-流式应答"，Harness 是"任务-多步-可中断-可恢复" |
| **状态模型冲突** | 网关用 SQLite 存对话历史；Harness 要工作目录 + 文件系统 + 命令执行 |
| **安全边界冲突** | ★ 网关跑在宿主、被容器通过 18790 访问；给它加"执行 shell"= **把宿主执行权暴露给容器**。这与我们费大力气做的 `netlock` 出站封网**方向完全相反** |
| **稳定性冲突** | Harness 是长任务、易崩溃、要重启恢复；网关必须常驻稳定 |

**推荐架构（旁路三件套）**：

```
                        ┌─────────────────────────────────────────┐
  O2OA 容器 ──18790──>  │  o2-agent-gateway  (保持轻量、稳定、常驻)  │  只做协议翻译
                        │   + 内置工具（含 kb_search/时间/计算）     │
                        └───────────────┬─────────────────────────┘
                                        │ 可选：把 harness 包装成一个 tool
                                        ▼
                        ┌─────────────────────────────────────────┐
   浏览器/CLI ─直接─>   │  agent-harness (独立进程, :8092)          │  任务编排
                        │   工作目录受限 = D:\O2OA\workspace\       │
                        │   命令白名单 / 无网络 / 只读挂载知识库      │
                        └─────────────────────────────────────────┘
```

**接入方式二选一**：

| 方式 | 优点 | 缺点 |
|---|---|---|
| **① 作为网关的一个 tool**：`run_agent_task(goal)` → 调 :8092 | O2OA 里就能用 | 长任务会撑爆 O2OA 的 SSE 等待体验 |
| **② O2OA 低代码发起**：流程/门户调 :8092，结果写回 O2OA 表单 | 符合长任务语义、可异步、有留痕 | 需要做 O2OA 侧的触发（低代码，成本可控） |

**建议：② 为主，① 作为轻量任务的快捷方式。**

**关于 "deepseek CLI / OpenClaw" 具体选型**：
- 我没有对 OpenClaw 做实测，**不做能力背书**。请先明确它解决的具体问题（是"多步任务编排"还是"代码生成+执行"？）。
- 若要落地，建议先做一个**最小 PoC**：给它一个只读知识库 + 一个受限工作目录，跑通"读文档→写报告"这类单链路任务，再评估是否值得产品化接入。
- ⚠️ **本机 VRAM 约束**（用户环境已知）：4B 常驻已占资源，Harness 若需 27B 级模型只能按需加载，与常驻 chat 冲突 → 需要排队机制或错峰。

## 2. 关于"AI 网关随 O2OA 一起启动"—— ✅ 应当做，但**不能用 docker compose 做**

**诉求合理**：现在 `start_o2oa.bat` 只起容器（compose up + netlock），AI 侧要另行双击 `start_ai_stack.bat`。
漏起 → AI 助手静默不可用（且有 `dns:127.0.0.1` 隔离，用户很难自行诊断）。

**为什么不能塞进 docker-compose**：
1. 后端是**宿主原生进程**（Windows exe + ROCm，依赖宿主 GPU 驱动）——容器化会丢掉 ROCm 加速；
2. 网关是宿主 venv Python 进程；
3. 硬塞会导致"O2OA 起来了但 AI 不可用"这种更难排查的半残状态。

**推荐实现：把 `start_ai_stack.bat` 接入 `start_o2oa.bat` 的启动链**

```bat
:: start_o2oa.bat 新增步骤（在 netlock 之后）
echo [3/3] 拉起 AI 侧（推理后端 + 适配网关）...
call "%~dp0gateway\start_ai_stack.bat"
```
并在 `stop_o2oa.bat` 里增加对应停止逻辑（结束 llama-server 与网关 python 进程）。

**必须配套的 3 项改进**（当前缺失，会导致"看起来启动了其实没起来"）：
1. **幂等检测**：启动前先探 `:8088/:8089/:18790`，已监听则跳过（避免双开占用端口）；
2. **就绪等待**：llama-server 加载模型要 5-15 秒，脚本应轮询 `/health` 而不是 `timeout /t 5`；
3. **失败可见**：任一环节失败要**明确报错并 pause**，不能静默继续。

**更优选项（推荐评估）**：用 **Windows 任务计划程序（开机自启）** 或 **nssm 注册为服务** 托管 AI 栈，
实现"开机即在"，比"随 O2OA 启动"更可靠——因为 AI 栈是常驻基础设施，不应与容器生命周期强绑。

## 3. 优先级建议（按 ROI 排序）
