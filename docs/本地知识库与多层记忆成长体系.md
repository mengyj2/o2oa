# O2OA 本地知识库 · 多层记忆 · 成长感知体系

> 版本：2026-09-21 ｜ 适用：本地断云部署的 O2OA 10.0.2 + AI 网关（端口 18790）
> 目标：让本地 O2OA 的 AI 助手能 RAG 检索 O2OA 自身的资料、操作经验与业务知识，并具备「持续学习 / 自我反思 / 成长可观测」的能力。

---

## 0. 为什么需要这套体系（定位）

用户诉求分三层，本方案逐层落地：

1. **资料 RAG**：把 O2OA 技术说明书、操作手册、版本改进点、软件自身的 API 资料整理进本地知识库，让 AI 能检索学习。
2. **经验 RAG**：把操作过程中的经验、问题解决、流程、业务本身提取总结进 RAG，让 AI 越用越懂业务。
3. **能力底座**：本地向量库 + 多层记忆系统 + Clawith 成长感知系统。

结论先行：**O2OA AI 网关内已自带一套可用的 RAG 内核**（SQLite 向量库 `data.db` + `qwen3-embed` 向量化 + `rag_retrieve` 融合检索 + `kb_search/kb_save`），`docs` 表自带 `category`/`permission` 字段——天然就是「本地向量库 + 多层命名空间」的底座，**无需另起炉灶**。本体系在其上补齐：① 资料灌库链路；② 多层记忆 taxonomy；③ 成长感知闭环（入库/反思/账本）。

## 2. 本地向量库（RAG 内核）

| 项 | 实现 | 说明 |
|---|---|---|
| 存储 | `D:\O2OA\gateway\data.db`（SQLite，WAL） | 单文件，零运维 |
| 文档表 `docs` | `id,title,category,content,creator_person,permission,meta,updated` | `category`=分层；`permission=[]`=对所有人可见 |
| 向量表 `chunks` | `doc_id,seq,text,embedding(BLOB,float32)` | 每块一条，余弦检索 |
| 嵌入 | `qwen3-embed` @ `http://127.0.0.1:8089/v1/embeddings` | 由 `embed_base`/`embed_models` 配置 |
| 分块 | `chunk_text(size=500, overlap=60)` | 按段落边界切分 |
| 检索 | `rag_retrieve`：向量分(0.6)+rerank分(0.4) 归一化融合 | rerank 不可用时回退纯向量 top_k |
| 权限 | `visible_docs(perms)`：空权限列表=管理员视角全可见 | RAG 主链路与 `kb_search` 同权 |

> rerank 端点 `8092` 默认关闭（llama-server 需加 `--reranking` 才启用）。当前向量融合已够用；需要更高精度时，给 embed 服务加 `--reranking` 并把 `rerank_enable` 置 true 即可。

## 3. 多层记忆 Taxonomy（category 命名空间）

| 层 | category 值 | 内容来源 | 是否本次已灌 |
|---|---|---|---|
| L0 | （不入库，在上下文） | 当前对话 | — |
| L1 | `ops_experience` | 操作经验/问题解决（脚本内置 12 条 seed） | ✅ 12 篇 |
| L2a | `o2oa_manual` | O2OA 技术/操作说明书（o2oa高级应用开发/docs） | ✅ 8 篇 |
| L2b | `o2oa_api` | O2OA 自身 REST API 目录（describe.json + api.json） | ✅ 14 模块 |
| L2c | `o2oa_ops` | 我们自己的运维/方案文档（docs/） | ✅ 12 篇 |
| L2d | `o2oa_version` | 版本/部署改进纪要 | ✅ 1 篇 |
| L3 | `business_process` | 业务 SOP（由 `kb_reflect` 从经验合成） | 待 reflect 生成 |
| L4 | `ai_synthesis` | 合成知识/AI 行为准则（reflect 产物） | 待 reflect 生成 |

扩展层（已有但非本次主灌）：`智能助手沉淀`(kb_save)、`财务制度`、`运维` 等，按业务需要继续补。

**当前规模**（截至 2026-09-21 实跑）：52 文档 / 451 向量块，跨 9 个分层。

## 4. 入库链路（持续把资料变知识）

### 4.1 一次性批量灌库（已实跑）
脚本 `tools/ingest_o2oa_kb.py`（仅标准库，无依赖）：
```bash
# 全量灌库（幂等，重复跑=更新）
python tools/ingest_o2oa_kb.py
# 只灌某一层
python tools/ingest_o2oa_kb.py --cat o2oa_manual
# 校验检索命中
python tools/ingest_o2oa_kb.py --verify
```
它走网关 HTTP 接口 `/idx-gateway-doc/update`（服务进程内 `reindex_doc`，避免直接锁 DB），按 category 分层写入。

### 4.2 AI 在线持续入库（运行时工具）
`kb_ingest`（仅 analyst/manager）：
- 第一步（不带 `confirm`）：预览将入库的文件清单与分层；
- 第二步（`confirm=true`）：把 `paths` 指向的 `.md/.txt/.json/.html` 灌入指定 `category` 层并自动向量化。
```json
{"name":"kb_ingest","paths":["D:\\O2OA\\o2oa高级应用开发\\docs"],"category":"o2oa_manual","confirm":false}
```

## 5. 成长感知闭环（让系统「越用越懂」）

三个工具 + 一张账本，构成可观测的成长回路：

### 5.1 `kb_reflect`（经验 → SOP 合成，核心）
- 收集 `ops_experience` 文档 + `feedbacks` 反馈；
- 用 chat 模型（qwen3.8-27b）提炼 3–8 条「场景+做法+原理」SOP，标注适用分层；
- 两步：先 `confirm=false` 出草案预览，用户确认后 `confirm=true` 落盘为 `ai_synthesis` 文档并写 `growth_ledger`。
- 实测示例产出：cookie 污染专用客户端、动态表走 designer、设计四层闸、QEMU 容器重启、外部 MySQL 三道门——均为高质量可复用知识。

### 5.2 `growth_report`（成长账本汇报，只读，全角色可用）
输出：各分层文档数、向量块数、反馈统计、历次入库/反思事件、下一步建议（如「business_process 层为空，建议补充」）。

### 5.3 `growth_ledger` 表
每次 `kb_ingest` / `kb_reflect` 成功都记一条 `(ts, kind, payload)`，供 `growth_report` 与未来趋势分析消费。

### 5.4 成长回路示意
```
操作 → 经验沉淀(ops_experience / kb_save)
     → 用户反馈(feedbacks)
     → kb_reflect 周期性反思 → 合成 business_process / ai_synthesis
     → RAG 检索质量提升 → 下次操作更准 → 更多经验 …
     （每一步均落 growth_ledger，growth_report 可观测）
```

## 6. 与 Clawith 成长感知系统的对接

O2OA 侧的「知识 + 记忆 + 成长账本」是权威知识源；Clawith 作为另一智能体，可通过以下方式消费：

1. **MCP 桥（推荐扩展）**：把 O2OA 网关的 `kb_search` / `growth_report` 包装成一个 MCP server（复用 `clawith-memory-mcp` 技能的服务框架，bind 到 `0.0.0.0:8765/mcp`），Clawith 的 native agent 通过 `agent_tools` 绑定即可在对话中检索 O2OA 知识库、读取成长账本。
2. **共享向量库**：若 Clawith 与 O2OA 网关同机，Clawith 记忆 MCP 可直接指向同一 `data.db`（只读）做跨体记忆。
3. **反向沉淀**：Clawith 解决 O2OA 问题时，调用 O2OA 网关 `kb_ingest`/`kb_save` 把结论回灌，形成双体共同成长的闭环。

> 当前本方案已完成 O2OA 侧（向量库+多层记忆+成长闭环）并实跑验证；Clawith 侧 MCP 桥为下一阶段扩展点（技能 `clawith-memory-mcp` 已具备框架）。
