# 本地辅助服务的持久化：为什么"看门狗"不是答案

> 场景：给 O2OA 配了一个宿主机上的 Python 辅助服务（本地验证码服务）。
> 服务能跑，但**重启就没了**。怎么让它"一直都在"？

## 1. 先分清三种"持久化"

| 层次 | 做法 | 性质 |
|---|---|---|
| **手工级** | 双击 bat 启动 | 关了窗口就没了 |
| **外挂级** | 看门狗进程周期探活、挂了就拉起 | 只是把"进程活着"挪到另一个进程里，**仍然不是系统的一部分** |
| **声明级** | 服务纳入编排（`docker-compose` 的 `restart: unless-stopped`） | 写在代码里、随分支走、可复现、可审计 ✅ |

**结论：要"代码级持久化"，就把服务变成编排的一部分，而不是外面挂一个看门狗去盯着它。**

## 2. 为什么看门狗方案不够

1. **它自己也需要被启动**——问题只是推后了一层（还得再挂个 VBS、计划任务或服务）。
2. **它不在版本库里表达任何东西**——`git diff` 看不出"这个服务应该一直跑"。
3. **它掩盖了错误的架构**——本机实测中，看门狗逻辑正确（每 30s 正确判定并拉起），
   但真正的问题（服务自身启动失败）被它反复重试的噪音淹没了。
4. **换台机器就失效**，而 compose 是 `docker compose up -d` 一句。

## 3. 容器化的具体收益（本项目实测）

服务改成 compose 的一个 service 后：

- **自愈**：`restart: unless-stopped` 由 Docker 引擎保证，崩溃自动拉起；
- **自启**：Docker Desktop 起来它就起来，与 O2OA 同生命周期，**不需要开机脚本**；
- **打包**：`Dockerfile` + compose 片段随分支走，`git clone` + `up -d` 即可复现；
- **顺带解决网络白名单**：与 o2oa 同在 `172.16/12` 内，断网脚本无需为它开口子；
- **顺带解决时区**：`Dockerfile` 里 `apk add tzdata` 固定 `Asia/Shanghai`，日志不再差 8 小时。

## 4. 关键设计：让同一份代码既能跑容器也能跑宿主

不要让容器形态和宿主形态各维护一份配置 —— 用**环境变量承担"部署拓扑"**：

| 配置项 | 容器里 | 宿主直跑 |
|---|---|---|
| O2OA 地址 | `http://o2oa-server:9090` | `http://localhost:9090`（默认值） |
| 对外注册地址 | `o2oa-mailservice:8095` | `192.168.65.254`（默认值） |
| 数据目录 | `/data`（挂载卷） | 源码目录（默认值） |

于是**数据文件里刻意不写这三项**，两种形态自动各自正确。

### 4.1 配置优先级：文件 > 环境变量 > 默认值

```
DEFAULT_CONFIG  <  mail.json（运行时文件）  <  O2OA_MAIL_* 环境变量
```

⚠️ **反直觉但必须**：让**文件优先于环境变量**。因为界面保存写的是文件；
若环境变量优先级更高，用户在界面上填的值会被**静默忽略** —— 极难排查。

⚠️⚠️ **compose 里绝不要声明凭据类环境变量**：`${VAR:-}` 在 `.env` 缺省时传入**空串**，
而空串是有效值，会覆盖掉界面上填好的授权码。凭据一律走挂载卷里的文件。

## 5. 一个必须知道的环境事实

**从 AI 会话（工具调用）启动的进程会被会话回收**，`DETACHED_PROCESS` 也不行。

本机实测：
- `Popen(..., creationflags=DETACHED_PROCESS|CREATE_NO_WINDOW)` → 命令一结束进程就没了；
- `schtasks`、WMI `Win32_Process.Create`、`Start-Process` → **全被安全策略拦死**。

⇒ **常驻进程的最后一公里只能由用户双击 bat、或登录自启完成**（或直接做成容器）。

## 6. 排查清单：服务"莫名失联"时的顺序

1. 端口在听吗？`netstat -ano | grep ":PORT "` / `Get-NetTCPConnection`
2. 进程还在吗？注意**venv 的 `python.exe` 是重定向器**，`Popen.pid` 与真实监听 PID **不是同一个**（本机实测 29692 vs 2468）⇒ 让服务自己 `os.getpid()` 写 PID 文件，别在外部猜。
3. 服务自己的日志怎么说？（O2OA 侧只会给你一句 `CodeFactory create error`，没有信息量）
4. 网络通吗？注意断网脚本会掐掉容器内的**域名解析**，只能用 IP / `extra_hosts`。
5. 注册还在吗？心跳超时会话表条目会被清（见 `o2oa_local_mail_code_service`）。

## 7. 反模式清单

- ❌ 服务靠"双击 bat"活着 —— 关了窗口就没了
- ❌ 用看门狗掩盖服务自身启动失败 —— 先去读服务日志
- ❌ 在外部脚本里 `save_pid(Popen.pid)` —— venv 下 pid 会错
- ❌ 容器里不装 tzdata —— 日志时间差 8 小时，排查必错
- ❌ 把凭据写进 compose 的 `${VAR:-}` —— 缺省时是空串，静默覆盖用户配置
