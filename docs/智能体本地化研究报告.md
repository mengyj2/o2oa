# O2OA 智能体本地化配置研究报告

> 2026-09-19 | 结论：**OpenClaw / Hermes 不能直接配上，但可以作为推理后端接入——需要在中间自建一层"协议适配网关"**（约 600~900 行代码，可行性已从源码层面完全验证）。

---

## 一、现状与报错根因

知识库索引页报错：

```
POST connect connection error, address: http://127.0.0.1:7080/app/api/idx-gateway-doc/list/paging/1/size/15
Connection refused
```

- 上一步已把"是否启用智能体"配为"是"，但 `o2AiToken` 仍为空、网关地址指向官方云（容器内 7080 不通）
- 知识库索引页的放行条件是 `enable || token/baseUrl 任一非空`（`ActionListPaging` 源码 line 38-42，判断写得很松），所以页面放行了、请求打到 7080 → 连接拒绝
- **根因**：O2OA 的"智能体"（知识库 RAG、MCP、对话记录、线索管理）全部是**云端 SaaS 网关协议**，开源版只是内置了客户端

## 二、O2OA 智能体网关协议全量契约（源码逆向）

基址 = 设置页的"智能体服务地址"（`o2AiBaseUrl`），认证 = `Authorization: Bearer <o2AiToken>`。

| 端点 | 方法 | 用途 | 请求体（已知） | 响应 |
|---|---|---|---|---|
| `/infra-auth/who` | GET | 探活/自动配置 | — | 200 即可 |
| `/ai-gateway-completion/generate` | POST | **对话核心**（chat/rag/mcp 三模式） | ChartWi：`{input, clueId, person, thinkingEnabled, generateType(chat\|rag\|mcp\|auto), referenceIdList, permissionList, endpointName}` | **SSE 透传**（O2OA 逐事件转发给前端，与 aiChat 路径同格式 = OpenAI chunk） |
| `/idx-gateway-doc/update` | POST | 文档入库（知识索引） | DocIndex：`{id, title, content, sourceId, processId, processName, creatorPerson, creatorUnit, permissionList, questionEnable, createDateTime, updateDateTime}` | ActionResponse |
| `/idx-gateway-doc/list/paging/{page}/{size}` | POST | 知识索引列表/搜索 | `{search}` | `{data:[DocIndex...], count}` |
| `/idx-gateway-doc/delete` | POST | 删除索引 | flag/id | ActionResponse |
| `/gateway-doc/upload/{id}/mode/replace` | POST(multipart) | 附件上传索引（pdf/docx/txt/md/pptx/xlsx） | 文件二进制 | ActionResponse |
| `/ai-gateway-endpoint/create\|get\|update\|delete\|list/paging` | POST/GET | 网关侧模型注册表（保存时同步） | AiModel | ActionResponse |
| `/ai-gateway-mcp/create\|get\|update\|delete\|list/paging` | POST/GET | MCP 服务器注册表 | McpConfig | ActionResponse |
| `/ai-gateway-completion/write/extra` | POST | 写会话补充 | — | ActionResponse |
| `/ai-gateway-completion/list/paging/{page}/{size}` | POST | 会话记录列表 | 分页 | `{data, count}` |
| `/ai-gateway-clue/list/paging`、`/ai-gateway-clue/delete` | POST | 对话线索管理 | 分页/删除 | `{data, count}` |

**三个决定可行性的源码事实**：
1. `o2Chat()` 对 generate 的响应**逐事件原样透传**给前端（不解析），所以网关吐 `data: {"choices":[{"delta":{"content":"..."}}]}` 格式即可，与现有 aiChat 路径完全一致
2. 走 o2Chat 路径的条件是 `o2AiEnable && baseUrl && token 三者非空`——网关建好后给 token 随便设一个非空值即可全量接管
3. `InitConfigTask` 定时任务：token 非空 + enable=true → 全部探测块跳过，**配置永久稳定**

## 三、OpenClaw 调研结论

- 定位：自托管多渠道个人 AI 助手**网关**（WhatsApp/Telegram/Slack/Discord 等统一接入），中心是 WebSocket 控制面 `ws://127.0.0.1:18789`
- **关键可用点**：网关同时暴露 **OpenAI 兼容 HTTP API**（`POST http://127.0.0.1:18789/v1/chat/completions`，Bearer token 鉴权）——任何讲 OpenAI 协议的客户端都可以把 OpenClaw 当"带工具/技能的 agent 大脑"
- 能力：agent 会话管理（JSONL 持久化）、技能/工具执行（shell、浏览器、文件）、cron、多模型（本地 Ollama 或远程 Claude/GPT）
- **与本需求的关系**：它不认识 O2OA 的 `/ai-gateway-*`、`/idx-gateway-*` 协议 → **不能直接填进"智能体服务地址"**；但可以作为适配层的**推理/工具后端**
- 本机现状：**未安装**（`~/.openclaw` 不存在，18789 端口无服务）

## 四、Hermes 调研结论

- 定位：与 OpenClaw 同类的本地个人 Agent（Python 生态），网关 `hermes gateway` 监听 `127.0.0.1:8642`，暴露 **OpenAI 兼容 `/v1/chat/completions`**
- **MCP 双向**：既能当 MCP client 挂任意 MCP server（`~/.hermes/config.yaml` 的 `mcp_servers`），也能 `hermes mcp serve` 把自己暴露成 MCP server
- 多渠道消息网关 + cron + 技能，生态里有 hermes-mcp / agentmcp 等桥接件
- **与本需求的关系**：同 OpenClaw——协议不匹配不能直连，可作适配层的推理/工具后端；**MCP 生态支持比 OpenClaw 更标准化**
- 本机现状：**未安装**（`~/.hermes` 不存在，8642 端口无服务）

## 五、可行性判定

| 方案 | 判定 | 说明 |
|---|---|---|
| 直接把 o2AiBaseUrl 填 OpenClaw/Hermes | ❌ 不可行 | 协议完全不匹配（私有 REST vs OpenAI） |
| 自建 o2-agent-gateway 适配层 | ✅ 可行（推荐） | 协议契约已 100% 逆向；SSE 透传机制使实现大幅简化 |
| 保持现状（仅对话） | ✅ 已可用 | 知识库/MCP 管理页会报错但无副作用 |

## 六、推荐架构

```
O2OA (x_ai_assemble_control)
    │  o2AiBaseUrl + Bearer 本地token（O2OA 私有协议）
    ▼
┌────────────────────────────────────────────┐
│  o2-agent-gateway（自建，Python/Node 薄层）  │
│                                            │
│  /ai-gateway-completion/generate           │
│    ├─ chat → 转发推理后端（SSE 重播）        │
│    ├─ rag  → 向量检索 → 拼上下文 → 推理      │
│    └─ mcp  → 工具调用循环（阶段2）           │
│  /idx-gateway-doc/*  → 本地向量库(SQLite)   │
│  /gateway-doc/upload → 附件解析→入库        │
│  /ai-gateway-endpoint|mcp|completion|clue/*│
│    → 本地 CRUD 表（管理页数据源）            │
└──────────────┬─────────────────────────────┘
               ▼
   推理后端（三选一，可并存）：
   ① LM Studio :1234（现成，glm-4.7-flash + 小型 embedding 模型）
   ② OpenClaw :18789 /v1/chat/completions（带技能 agent，未装）
   ③ Hermes  :8642 /v1/chat/completions（MCP 生态好，未装）
```

要点：
- **embedding**：LM Studio 加载小型嵌入模型（如 bge-m3 / nomic-embed，量化后 <1GB，不挤占 4GB VRAM 的推理空间）
- **向量库**：SQLite + numpy 余弦即可（单机、文档量 O2OA 内容管理场景足够），无需引入向量数据库
- **权限**：DocIndex 带 `permissionList`（人员/部门 DN），检索时按 O2OA 传入的 permissionList 过滤——本地网关可先做简化版（管理员全可见）
- **reasoning_content 陷阱**：适配层统一给推理请求加 `reasoning_effort:none`，之前的 ActionChat 字节码补丁保留但不再是关键路径

## 七、分阶段实施计划

**阶段 1（核心，预计一次会话可完成）**
1. Python 实现 o2-agent-gateway（FastAPI/Flask + SSE）：who / generate(chat,rag) / idx-gateway-doc(update,list,delete) / upload / endpoint+mcp+completion+clue 的 CRUD 桩
2. SQLite 存 DocIndex + 分块 + embedding 向量；LM Studio 拉一个嵌入模型
3. O2OA 配置：`o2AiBaseUrl = http://192.168.1.5:18790/app/api`，token 设本地值
4. netlock 增加白名单：容器 → 192.168.1.5:18790
5. 端到端验收：知识库索引页不再报错、内容管理文档入库、"同步知识库"成功、RAG 问答能引到文档内容

**阶段 2（增强，可选）**
- generate 的 mcp 模式：接入 MCP servers（Hermes 或原生 MCP client）
- 把推理后端切到 OpenClaw/Hermes（获得技能执行、定时任务、多渠道能力）
- 会话记录/线索管理持久化完善

**风险与注意**
- ActionResponse 包裹格式（`{type:"success", data, count}`）按 O2OA 惯例实现，个别端点字段名可能需 1-2 轮联调（有源码在手，改动快）
- 前端 RAG 引用展示格式（引用块/出处）未知，首版先纯文本注入 prompt，引用展示后续对齐
- 4GB VRAM：嵌入模型与推理模型分时加载或用 CPU 跑 embedding

## 八、需要你决策的两件事

1. **范围**：先做阶段 1（知识库 RAG + 对话，全部本地），还是连阶段 2 一起？
2. **推理后端**：阶段 1 用现成的 LM Studio（推荐，零新增安装）；OpenClaw/Hermes 是否要装、装哪个（Hermes 的 MCP 生态更成熟，OpenClaw 的技能/渠道更丰富）——不装也不影响阶段 1。
