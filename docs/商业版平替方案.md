# O2OA 社区版「商业版平替」可行性分析与实施方案

> 编制日期：2026-09-19
> 目标环境：本地 Docker 自托管 O2OA 社区版 10.0.2（已断云 + 已接本地 AI 网关）
> 本文档为**纯分析方案**，未对系统做任何变更。所有结论均基于实测取证。

---

## 〇、结论摘要（先看这里）

| 需求 | 可行性 | 关键前提 | 工作量 |
|---|---|---|---|
| ① AI 流程优化 / 智能报表分析（智能问答、流程辅助、报表自然语言查询） | **可行（高）** | 复用已有本地推理网关 | 中 |
| ② 把免费应用都下载到本地 | **受限（关键卡点）** | 必须先解决断云 vs 市场的矛盾 | 低（打通后） |
| ③ 低代码搭建 7 大业务模块平替 | **可行（高，但工作量大）** | 用流程引擎+表单+数据中心自建 | 高（分阶段） |

**一句话总结**：①③ 靠你现有能力就能实现；② 被你自己的断云策略挡住了，需要做一个明确的取舍决策。

## 一、取证结论（硬证据）

### 1.1 应用市场（关键卡点）

**实测结果：应用市场在当前断云配置下完全不可用。**

```
GET  /x_program_center/jaxrs/market/list/category          → success，但 valueList 为空
POST /x_program_center/jaxrs/market/list/paging/1/size/10  → success，但 data 为空数组
POST /x_program_center/jaxrs/collect/login                 → error: "O2OA collect(o2cloud) interface is disabled by local netlock policy."
GET  /x_program_center/jaxrs/market/cloud/unit/is/vip      → value: false（拿不到云端 VIP 令牌）
```

**根因（读官方源码 `x_program_center.war!/describe/sources/.../market/` 确认）**：

- `ActionListPaging` / `ActionDownload` **全部走 collect 通道**：
  ```java
  String token = Business.loginCollect();                    // 需要云平台登录
  ConnectionAction.get(Config.collect().url(...), token);    // 经 collect.o2oa.net 拉数据
  ```
- `ActionDownload` 还额外校验 `app.getHasInstallPermission()`，权限来自云端。
- 而你的 `patch_collect_lock.sh` 把 `/jaxrs/collect/*` **整体 403 物理切断**（entrypoint.sh:80-83）。
- **接口返回 success 但数据为空**——这正是被封锁后的典型表现（不是报错，是静默空）。

**这意味着我上一轮"市场不受断云影响"的判断是错的**，此处更正：market 模块的**前端页面**独立，但它的**数据源**依赖 collect 通道，断云等于断粮。

**云端侧仍活着**（可回滚）：
```
https://collect.o2oa.net/                                  → 200
https://collect.o2oa.net/x_program_center/jaxrs/collect/echo → 401（路径存在，需鉴权）
```
即：开云后市场能恢复，云平台要账号密码（`collect.json` 的 `name`/`password`），你当前这两个字段是空的。

### 1.2 离线安装通道（破局关键）

`ActionInstallOffline`（`POST /x_program_center/jaxrs/market/install/offline`，multipart）**不校验云端权限**，逻辑是：

```java
if (bytes != null && bytes.length > 0) {
    InstallData installData = this.install(app, bytes);   // 直接解包安装
    ...
}
```

解包支持 4 种内容（`setup.json` 描述应用元信息）：
| 目录名 | 类型 | 说明 |
|---|---|---|
| `custom/` | 自定义应用 | 打包成 custom.zip 部署 |
| `xapp/` | 模块包 | **`.xapp` 文件 = 流程/门户/内容/统计/服务模块** |
| `web/` | 前端资源 | web.zip |
| `config/` | 配置 | config json 注入 |

**结论：只要拿到 zip 包，断云也能离线安装。** 问题只在于"包从哪来"——免费应用的包需要从云端下载，而云端要开云。

### 1.3 低代码程序化接口（自建模块的基础）

流程设计器（`x_processplatform_assemble_designer`）接口完备，**全部带源码可查**：

| 能力 | 接口 |
|---|---|
| 创建流程 | `ActionCreate` |
| 导出（生成 xapp） | `ActionLeadOut` |
| 导入 | `ActionImport`（`Applications.joinQueryUri("input","cover")`） |
| 表单 | `form/ActionCreate`、`ActionEdit` |
| 数据字典 | `ApplicationDict` |

数据中心（`x_query_*`）支持 `table`（数据表）、`view`（视图）、`stat`（统计）、**`neural`（神经网络查询）**、`statement`（JPQL/SQL 语句）——**这是智能报表的天然基础**。

### 1.4 你已有的 AI 底座

`gateway/o2_agent_gateway.py`（FastAPI，:18790）已实现四种模式：

- **chat** — 对话推理
- **rag** — 全文检索 + 向量（`data.db` SQLite 已建索引，`embed` 用 qwen3-embed）
- **kb** — 知识库文档索引（`idx-gateway-doc/*`）
- **mcp** — HTTP 型工具调用（`exec_tool`）

配置：`chat_model=qwen3.5-4b`，`rag_top_k=6`，已跑通端到端冒烟（`ai_smoke.js` → `{"ok":true}`）。

**这意味着"智能问答"你已经有了**，"流程辅助 / 报表自然语言查询"只是在此之上加两个专用提示词编排层。

## 二、方案一：AI 流程优化 / 智能报表分析

### 2.1 目标拆解

| 商业版能力 | 平替实现 | 复用现有 |
|---|---|---|
| 智能问答（AI 助手） | 已实现 | ✅ 网关 chat 模式 |
| 流程辅助（填单建议/流程推荐） | 网关 + 流程元数据注入 | ✅ 网关 chat |
| 报表自然语言查询（NL2SQL/NL2Query） | 网关 + 数据中心语句接口 | ✅ 网关 + `statement`/`neural` |

### 2.2 报表自然语言查询架构

```
用户："上个月各部门报销总金额是多少？"
   ↓
[O2OA 门户/表单 里的自定义组件]
   ↓ 把问题 + 数据表结构(来自 x_query designer 元数据) 发给网关
[网关 :18790] 新增一个 /nl2query 智能路由
   ↓ 让 LLM 把自然语言翻译成 JPQL / SQL 语句
[O2OA x_query_assemble_surface/jaxrs/statement] 执行语句
   ↓ 返回结果集
[网关] 让 LLM 把结果集转成自然语言 + 图表配置
   ↓
用户看到："上月报销合计 ¥12,345，其中技术部占比 43%……"
```

**关键设计点：**

1. **不能让大模型直接生成 SQL 打到库上**（注入风险 + 幻觉风险）。正确做法：
   - 预先在数据中心建好**受限视图**（只暴露必要字段）；
   - LLM 只负责「选视图 + 填参数」，输出**受控 DSL**而非裸 SQL；
   - 网关侧做白名单校验后再执行。
2. **表结构注入用 RAG**：把数据表/视图的元数据做成知识库文档，用户提问时先检索相关表，再让 LLM 生成查询——这样能适配表很多的情况，也避免提示词过长。
3. **流式返回**：复用网关已有的 SSE 首帧 `event:status` + `event:message` 机制。

### 2.3 流程辅助

在流程表单里挂一个自定义组件，调用网关：

- **填单辅助**：把表单当前已填字段 + 历史相似单据作为上下文，让模型补全/校验；
- **流程推荐**：把"流程清单 + 每个流程的适用说明"做成知识库，用户描述诉求，模型推荐该走哪个流程；
- **审批意见生成**：根据单据内容生成审批意见草稿。

**注意**：O2OA 表单自定义组件里发请求要跨域到 18790，需确认门户/CORS 配置；也可走 O2OA 服务管理（`x_program_center` 的 serviceModule）做后端转发，更规范。

### 2.4 风险与防护

| 风险 | 防护 |
|---|---|
| 模型生成错误查询 | 受控 DSL + 白名单 + 结果集空则回退提示 |
| 敏感数据外泄 | 网关全本地，不出网；查询结果按登录人权限过滤 |
| 4B 模型能力不足 | 报表洞察类任务可临时切换更大模型（如 glm-4.7-flash） |
| 注入攻击 | 绝不执行模型裸 SQL，只执行参数化模板 |

## 三、方案二：免费应用下载到本地

### 3.1 三个可选路径（需你决策）

**路径 A：临时开云 → 下载 → 再断云（推荐，最省力）**

1. 备份当前 `config/collect.json`（已消毒版本）；
2. 临时恢复 `collect` 通道（还原 `collect.json` 的 `server`/`name`/`password`，并临时停用 `patch_collect_lock`）；
3. 用 xadmin 登录后在应用市场页面批量安装免费应用 → **安装后立刻调 `{flag}/download` 把 zip 拉下来存本地**，形成离线包库；
4. 重新断云，之后所有安装都用 `install/offline` 离线安装。

> 前提：需要一个 O2 云账号（免费注册）。**这一步需要你提供账号或确认注册。**

**路径 B：纯离线，不碰云（最安全，但拿不到现成包）**

- 直接放弃"下载官方免费应用"，改为用低代码**自建等价功能**（即方案三）。
- 好处：不破坏断云策略，无外部依赖。
- 代价：免费应用里的成熟流程（固定资产、用车、通知公告等）要自己搭。

**路径 C：从公开渠道找现成 xapp/离线包**

- 社区/Gitee/GitHub 上有人分享 `.xapp` 导出文件，可用 `install/offline` 装入。
- 需要逐个甄别来源可靠性，**不保证覆盖"全部免费应用"**，且版本兼容性要验。

### 3.2 我的建议

**A + C 组合**：短期用 A 快速建"离线包库"（一次性开云把免费应用全拖下来），之后永久断云；同时用 C 补充社区里流通的优质 xapp。

**但必须明确**：这与"纯离线"初衷冲突，需要你拍板。**"既要完全断云、又要下载云端免费应用"在技术上矛盾**——因为免费应用的包就存在云端。

### 3.3 待你提供

- [ ] 是否有 O2 云账号？（路径 A 必需）
- [ ] 是否接受"一次性开云下载"？（安全取舍）
- [ ] 若都不接受，是否接受"全部自建"（路径 B）？

## 四、方案三：低代码搭建 7 大业务模块平替

### 4.1 总体思路

O2OA 社区版的定位就是"**开发平台**"，商业版的业务模块本质是「**流程 + 表单 + 数据 + 门户**」的组合。所以平替路径是：

```
每个业务模块 =  1个应用(Application)
             + N个流程(Process)      ← 走审批
             + N个表单(Form)         ← 数据录入
             + N个数据表(Table)      ← 数据沉淀
             + N个视图/统计(View/Stat)← 数据展现
             + 1个门户(Portal)        ← 首页看板
```

### 4.2 七大模块拆解

| 模块 | 核心流程 | 核心数据表 | 复杂度 |
|---|---|---|---|
| **人力资源管理** | 入职、转正、调岗、离职、合同续签、请假、加班、出差、证明申请 | 员工档案、合同、考勤汇总、积分 | ★★★★★ |
| **合同全生命周期** | 起草、审批、变更、用印、收付款申请、归档 | 合同档案、签约方、收付款计划 | ★★★★ |
| **公文管理** | 发文（拟稿→审核→会签→签发→编号→盖章→分发）、收文（登记→审核→批示→办理→传阅→归档）、督办 | 发文档案、收文档案、督办单 | ★★★★★ |
| **财务管理** | 费用报销、借款、付款申请、预算申请 | 报销单、付款单、预算 | ★★★★ |
| **PMS 项目协同** | 立项、任务分派、进度汇报、验收、复盘 | 项目、任务、工时、里程碑 | ★★★★ |
| **资产管理** | 采购申请、领用、调拨、盘点、报废 | 资产台账、分类、盘点记录 | ★★★ |
| **MinIO 集成** | —（是插件不是流程） | —（对象存储对接） | ★★ |

**关于 MinIO 的特别说明**：MinIO 是**外部存储插件**（VIP 应用），不是低代码能"搭"出来的。它的原理是"基于 apache vfs 扩展插件规范开发"的附件存储适配器。**平替方式**：自建一个 vfs 插件 jar，或直接用 O2OA 自带的文件存储 + 外部存储配置（`externalStorageSources.json`）。这一项与"低代码搭建"性质不同，需要单独评估。

**公文管理特别说明**：涉及红头模板、版式文件、国标《党政机关公文格式》，工作量最大，建议放最后。

### 4.3 实施策略：先立骨架，再填肉

**强烈建议不要 7 个模块并行做**，而是：

**第一阶段：打通"一个最小闭环"（做一个资产管理）**
- 目标：跑通「建应用 → 建数据表 → 建表单 → 建流程 → 建视图 → 发布 → 手机端可用」全链路；
- 产出：一套**可复制的模板方法论 + 自动化脚本骨架**；
- 意义：验证低代码程序化创建的可行性，后面 6 个模块就是复制。

**第二阶段：复制到中复杂度（PMS / 合同 / 财务）**

**第三阶段：攻复杂模块（人事 / 公文）**

**第四阶段：MinIO 等插件类单独处理**

### 4.4 关键技术决策点（待确认）

1. **程序化创建 vs 界面创建**
   - 程序化：写脚本调 REST 接口批量建（快、可复用、可版本化），但表单 HTML 结构复杂，容易踩坑；
   - 界面：在 O2OA 设计器里点（直观、所见即所得），但不可版本化、不可批量。
   - **建议：混合**——数据表/流程结构用脚本，表单版式在设计器里调。

2. **数据表用 O2OA 数据表 vs 直接建 MySQL 表**
   - O2OA 数据表（`x_query` Table）与流程数据天然打通，**推荐**；
   - 直接建 MySQL 表性能更好但集成度低。

3. **是否需要移动端**
   - 社区版自带移动门户，业务模块默认能上手机端。

## 五、优先级与建议路线图

```
第 0 步（决策）        → 你确认：市场取舍(A/B/C) + 是否要移动端 + 先做哪个模块
第 1 步（打地基）      → AI 能力增强：报表 NL 查询 + 流程辅助（复用现有网关，见效快）
第 2 步（建样板）      → 资产管理模块全链路跑通，固化成方法论
第 3 步（批量复制）    → PMS / 合同 / 财务
第 4 步（攻坚）        → 人事 / 公文
第 5 步（插件）        → MinIO / 其他存储集成
第 6 步（整合）        → 统一门户门户看板 + AI 助手入口
```

**为什么 AI 放第一步**：投入小、风险低、见效快，能立刻提升体验；且不依赖任何云端资源。

## 六、明确的能力边界（不承诺做不到的事）

1. **商业版原版二进制组件**（如 AI 流程优化引擎、智能报表内核）**拿不到**，只能做等效功能，不是"原厂原件"。
2. **VIP 应用**（人力资源管理、合同管理、企业网盘、OfficeOnline、MinIO、短信、OSS、APP 打包）**需要商务授权**，我不会做绕过授权的破解。
3. **"完全断云"与"下载云端免费应用"技术上互斥**，必须取舍。
4. 低代码自建的模块**功能对等但非原厂**，界面、流程细节与商业版不会完全一致，需要按你的实际业务调整。
5. 公文管理的**国标版式**部分工作量巨大，且可能需要版式编辑器支持。
