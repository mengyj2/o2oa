## 二、`.xapp` 文件的真实格式（重要）

这一点决定了排障方向，必须先明确。

**`.xapp` 不是 ZIP 压缩包，而是一个单文件 JSON 文本。**

依据 O2OA 服务端源码 `x_program_center` 模块的 `ActionCompareUpload.java`：

```java
String json = new String(bytes, DefaultCharset.charset);
WrapModule module = XGsonBuilder.instance().fromJson(json, WrapModule.class);
```

对应的前端代码在 `o2web/source/x_component_AppCenter/Main.js`：

```js
<input type="file" accept=".xapp" />
formData.append('file', this.file);
```

前端把整个文件作为一个 `file` 字段上传，服务端直接读字节流按 UTF-8 解码后做 Gson 反序列化为 `com.x.program.center.WrapModule`。**全过程没有任何解压动作，也不存在 `manifest.json` 之类的包内清单文件**，O2OA 不读取任何包内清单。

因此：

- ✅ 可以用记事本 / VS Code 直接打开 `.xapp` 查看内容（是格式化的 JSON）。
- ✅ 排障时可以自行用 JSON 工具校验语法。
- ❌ 不要尝试用解压软件打开，会失败。
- ❌ 不要改名成 `.zip`，不要往里面塞文件。

## 三、导入顺序（务必遵守）

数据字典是其他应用表单下拉选项、以及各应用间状态流转判断的公共基础，因此**必须最先导入**。

```
① 00_公共数据字典.xapp        ← 必选，最先导入（41 条字典）
        ↓
② 01_项目管理应用.xapp        ← 主线应用，project_no 是全局关联键
        ↓
③ 02_合同管理应用.xapp        ← 通过 project_no 关联项目
        ↓
④ 03_预算管理应用.xapp        ← 通过 project_no 关联项目
        ↓
⑤ 04_财务管理应用.xapp        ← 通过 project_no / contract_no / budget_no 三方关联
        ↓
⑥ 05_档案管理应用.xapp        ← 汇聚各应用的归档数据
        ↓
⑦ 06_人力资源管理应用.xapp    ← employee_no 作为人员主键向上述五大应用辐射
```

说明：O2OA 导入时并不强制依赖顺序（元素以 ID 落库，不做外键校验），但**顺序导入可以让字典先就位**，避免表单渲染时下拉选项为空、需要二次手工绑定。按上述顺序导入可以一次到位。

**人力资源管理应用的两个额外注意点**：

1. 它是**六个应用里组织依赖最重**的一个 —— 14 条流程的处理人脚本引用了
   「人力资源部 · 人事主管 / 部门负责人 / 考勤管理员」等身份。
   这些身份若不存在，**流程启动后找不到处理人**。建议在导入 06 之前先把
   人力资源部及其岗位在「组织管理」里建好。
2. 它的「查询配置」中有多条跨应用联查（`员工档案 ⟕ 人事变动`、
   `积分 ⟕ 档案`、`考勤 ⟕ 档案`、以及员工自助三方 LEFT JOIN），
   因此建议放在最后导入，确保被引用的五大应用元素已就位。

## 四、导入操作步骤

### 4.1 进入应用中心

1. 用管理员账号登录 O2OA（默认 `xadmin`）。
2. 首页 → 左侧导航找 **应用中心**（图标为四个方块）。
3. 进入后顶部有 **导入应用** 按钮。

### 4.2 上传应用包

1. 点击 **导入应用**。
2. 在弹窗中点击选择文件，选中 `00_公共数据字典.xapp`。
3. 确认上传。

### 4.3 处理冲突对比（关键环节）

上传后，O2OA 会调用 `/module/compare` 服务，把包内容与当前系统已有元素逐一对比，返回一个**冲突对比清单**。界面会列出每个元素的名称与冲突状态，需要你为**每个冲突项**选择处理方式：

| 选项 | 含义 | 使用场景 |
|---|---|---|
| **create**（新建） | 保留系统已有元素，新增包内元素 | 首次导入，或系统里已有同名但不同用途的元素 |
| **cover**（覆盖） | 用包内元素替换系统已有元素 | 升级迭代，想用新版本替换旧版本 |
| **ignore**（忽略） | 既不新增也不覆盖，跳过该项 | 系统里已有且不想改动 |

选择后点击确认，O2OA 调用 `/module/write/{flag}` 落库。

> **首次导入建议**：全选 **create**。因为此刻系统里通常没有同名元素，全选 create 不会产生任何副作用。
>
> **二次导入（升级）建议**：对本次修改过的元素选 **cover**，其余选 **ignore**，避免覆盖掉你在系统里手工改过的内容。

### 4.4 校验导入结果

依次检查：

1. **流程平台** → 应看到新建的六个应用（项目管理 / 合同管理 / 预算管理 / 财务管理 /
   档案管理 / 人力资源管理），每个点进去有表单、流程、数据字典三个页签。
   表单合计 **53** 个、流程合计 **42** 条。
2. **数据中心** → 应看到六个「××应用（数据中心）」，各有视图、统计、自建表、查询配置。
   视图合计 **40** 个、统计 **35** 个、自建表 **31** 张、查询配置 **31** 条。
3. **服务管理** → 应看到「公共数据（全局）」，内含 **41** 条字典。
4. **门户应用** → 应看到 2 个门户：合同管理门户（4 页）、人力资源管理门户（6 页）。
   人力资源管理门户含「人力资源首页 / 员工档案 / 人才市场 / 积分管理 / 考勤管理 / 员工自助」。

### 4.5 导入后必做的三项配置

导入包只包含**结构与定义**，以下三项与具体服务器环境相关，需要导入后手工确认：

1. **组织架构绑定**：各流程节点的处理人脚本引用了具体部门与职务名称，需保证系统组织架构中存在这些节点，否则流程启动后找不到处理人。

   | 脚本引用的部门 | 职务 | 使用场景 |
   |---|---|---|
   | 财务部 | 财务主管 | 各类流程的财务审核、财务付款环节 |
   | 法务部 | 合同管理员 | 合同审批流程的法务审核、签署登记 |
   | 综合办公室 | 档案管理员 | 项目归集、合同归档、档案著录与入库 |
   | 综合办公室 | 分管领导 | 合同 / 预算 / 人事的终审环节 |
   | **人力资源部** | **人事主管** | 员工入职/转岗/转正/离职、岗位发布、积分授予 |
   | **人力资源部** | **部门负责人** | 人事类流程的部门复核 |
   | **人力资源部** | **考勤管理员** | 请假 / 加班 / 出差 / 考勤确认（06 应用，依赖最重） |

   若你的组织架构命名不同，请修改对应流程节点的 `taskScriptText`。

2. **流程启动权限**：导入流程的 `startableIdentityList` 默认为空，表示**全员可启动**。若需要限定范围，在流程设计的「启动权限」处配置。

3. **自建表建表**：数据中心的自建表定义导入后，需要在自建表页面执行**创建数据库表**操作（O2OA 会按 `fieldList` 自动生成物理表）。数据库类型不同（MySQL / Oracle / PostgreSQL / 达梦等）生成的 DDL 也不同，由 O2OA 自动适配，无需手写 SQL。

### 4.6 自建表初始数据导入（可选）

如果希望预置基础数据（比如项目台账的初始项目清单、员工花名册），使用 `_excel/` 目录下的模板：

1. 打开 `_excel/` 下对应表的 `.xlsx`（文件名格式 `序号_应用名_表名.xlsx`）。
2. **删除第 2 行**（中文标题+类型说明行），它是给人工看的，导入时会多出一行脏数据。
3. 第 1 行即为自建表字段名，逐行填入数据。注意 `id` 列留空或填唯一字符串
   （O2OA 会生成主键）。
4. 数据中心 → 对应自建表 → **导入数据** → 上传 Excel。
5. 字段名必须与模板表头完全一致，顺序可有差异，但不能有多余列。

> 模板的列头已与 `.xapp` 内自建表 `fieldList` 的字段名做过**逐字比对**
> （31 个模板全部一致，含顺序），因此导入映射可直接匹配。

**建议导入顺序**（保证引用关系完整）：
`项目 → 合同 → 预算 → 财务 → 档案 → 人力`。
人力资源管理应用内部，应**先导「员工主表」**，再导转岗/转正/离职/岗位/积分/考勤等业务表
（这些表带 `employee_no` / `apply_no` 外键）。

## 五、常见问题排查

| 现象 | 原因 | 处理 |
|---|---|---|
| 导入时报「文件格式错误」 | 文件被当字符串处理时编码非 UTF-8 | 用记事本另存为 UTF-8（无 BOM），或重新从 `deliverables/` 取原始文件 |
| 导入后流程节点没有表单 | 节点的 `form` 字段为空 | 本版已修复，**42 条流程的 159 个人工节点全部绑定表单**（程序化校验 0 遗漏）。若仍遇到，检查节点 `form` 是否指向了不存在的表单 ID |
| 表单打开后下拉框为空 | 字典未导入或未绑定 | 先导入 `00_公共数据字典.xapp`；再检查表单字段的字典绑定 |
| 流程提交后提示「没有找到处理人」 | 组织架构中缺少脚本引用的部门 / 职务 | 按 4.5 节表格核对组织架构，或修改节点处理人脚本 |
| 视图 / 统计打开报错「表不存在」 | 自建表尚未在数据库建表 | 数据中心 → 自建表 → 点「创建数据库表」 |
| 查询配置报 SQL 语法错误 | 数据库类型与 SQL 方言不匹配 | 本包 SQL 使用标准 `LEFT JOIN` / `GROUP BY` / `ROUND`，MySQL 与 PostgreSQL 可直接使用；达梦 / 人大金仓需确认 `CURRENT_DATE` 写法 |
| 跨应用查询查不到数据 | 关联键未写入自建表 | 需配置流程结束后的数据写入逻辑，见《数据关联与共享机制说明》第三章 |

## 六、版本与再导入

本包内每个元素的 ID 均由设计阶段固定（如表单 `f1001001-project-base-form-00000000001`、流程 `p1001001-project-approve-0000000000001`），**跨版本保持稳定**。

这意味着：

- 二次导入同一应用包时，O2OA 能准确识别出「这是同一个元素的更新版」，选择 **cover** 即可完成升级，不会产生重复元素。
- 但**覆盖会丢失你在系统里对该元素的手工修改**。若你在系统里改过表单布局或流程走向，升级前请先导出备份。
