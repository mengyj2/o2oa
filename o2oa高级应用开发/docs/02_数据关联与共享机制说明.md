## 一、总体设计思路

### 1.1 为什么是「五应用 + 一主线」

五个应用不是五个孤岛，而是围绕**一个业务主线**展开的五个环节：

```
        立项              签约              用钱              花钱              留痕
   ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐
   │ 项目管理 │ → │ 合同管理 │ → │ 预算管理 │ → │ 财务管理 │ → │ 档案管理 │
   └──────────┘   └──────────┘   └──────────┘   └──────────┘   └──────────┘
        │              │              │              │              │
   project_no     contract_no     budget_no      expense_no     archive_no
        └──────────────┴──────────────┴──────────────┴──────────────┘
                         全部挂靠 project_no 主干
```

**`project_no`（项目编号）是全系统的关联主干**。任何一个合同、一笔预算、一张报销、一份档案，都能通过 `project_no` 回溯到它所属的项目。

### 1.2 跨应用数据共享的接口设计

O2OA 里跨应用共享数据，靠的不是外键约束（O2OA 本身不做数据库外键管理），而是**自建表 + 查询配置**这一组合：

| 层次 | 承载元素 | 作用 |
|---|---|---|
| **落库层** | 各应用的自建表 | 把流程表单里的关键字段，在流程流转时写入一张扁平化的业务表 |
| **关联层** | 关联键字段（`project_no` 等） | 让不同应用的自建表之间存在可 JOIN 的公共列 |
| **查询层** | 查询配置（SQL） | 用标准 SQL 做跨表 JOIN，产出面向业务的数据视图 |

这套设计的优点是：**不侵入 O2OA 内核**，全部通过平台原生能力实现；同时因为用的是标准 SQL，将来接 BI 工具、接数据大屏都很顺畅。

## 二、五大应用内部结构

**定位**：项目全生命周期的唯一权威数据源。

| **流程（7）** | 项目立项审批流程、项目进度风险评审流程、项目资金拨付审批流程、项目物资申请审批流程、项目结项审批流程、项目变更审批流程、项目任务分派流程 |
| **自建表（3）** | 项目主表、项目成员表、项目里程碑表 |
| **视图（8）** | 项目台账视图、立项审批台账、进度风险台账、资金台账、成本核算台账、物资台账、结项台账、任务台账 |
| **统计（6）** | 项目状态分布、项目类别分布、部门预算分布、项目进度统计、项目风险分布、项目成本偏差统计 |
| **字典（12）** | 项目类别、项目状态、币种、预算类别、费用类型、付款类型、合同类型、合同状态、档案类别、保密等级、档案状态、资金来源 |

**项目主表字段（18 个）** —— 这是全系统的核心表：

```
id            主键

project_name  项目名称
project_type  项目类别（字典：项目类别）
```

注意 `contract_no` 与 `budget_no` 两个字段：它们让项目主表能**反向指回**合同与预算，是双向关联的设计。


**定位**：把项目总预算拆解为可执行的预算额度，是成本控制的前置闸门。

| **视图（3）** | 预算台账视图、预算执行台账、预算执行预警视图 |
| **统计（3）** | 预算类别分布统计、部门预算统计、资金来源统计 |
| **查询（2）** | 预算执行汇总查询、项目预算关联查询 |

**预算主表字段（15 个）**：

```

budget_type, budget_year,
project_no      ← 关联项目
dept_name, fund_source,

```

```

                ↘ 退回    ↘ 驳回      ↘ 不批准
```

```
expense_type, applicant, apply_dept, apply_date,
```


**项目成本汇总表字段（10 个）** —— 这是**预计算的汇总表**，用于给项目看板提供快速读取：

```
id, project_no, project_name,
budget_total, expense_total, payment_total,
actual_cost, variance, variance_rate, update_time
```

其中 `variance = actual_cost - budget_total`（成本偏差），`variance_rate` 为偏差率。

**费用报销审批流程** —— 含**金额分级路由**：

```
报销申请 → 部门审核 → 分管领导审批 ─┬─ 金额 ≥ 5000 → 主要领导审批 → 财务审核 → 出纳支付 → 结束
                                  └─ 金额 < 5000 ─────────────────→ 财务审核
                       ↘ 退回修改         ↘ 驳回
```

分级条件脚本：

```javascript
// 分管领导审批 后置路由条件（≥ 5000 走高一级审批）
return this.data.expense_main.total_amount >= 5000;

// < 5000 直接进入财务审核
return this.data.expense_main.total_amount < 5000;
```

字段名 `expense_main` 是费用报销单在设计器里的模块分组名，`total_amount` 是组内的报销总金额字段。

## 三、跨应用数据共享机制（查询配置详解）

导入包内含 **13 条查询配置**，全部是跨表 JOIN 的 SQL。它们就是应用间数据共享的实际落地形态。

### 3.1 项目管理应用内的 3 条

**① 项目资金汇总查询** —— 项目主表 × 资金台账

```sql
SELECT p.project_no, p.project_name, p.total_budget,
       SUM(f.apply_amount)    AS applied,
       SUM(f.approved_amount) AS approved
FROM 项目主表 p
LEFT JOIN 资金台账 f ON p.project_no = f.project_no
GROUP BY p.project_no
```

用途：项目视角看资金申请与批复的累计额。

**② 项目合同关联查询** —— 项目主表 × 合同主表（**跨应用**，读合同管理应用的自建表）

```sql
SELECT p.project_no, p.project_name,
       c.contract_no, c.contract_name, c.contract_amount, c.contract_status
FROM 项目主表 p
LEFT JOIN 合同主表 c ON p.project_no = c.project_no
```

用途：在项目应用内直接看到该项目下的全部合同。**这条 SQL 是跨应用共享的直接证据**——项目管理应用在运行时读取的是合同管理应用创建的数据表。

**③ 项目档案关联查询** —— 项目主表 × 档案主表（**跨应用**，读档案管理应用）

```sql
SELECT p.project_no, p.project_name,
       a.archive_no, a.archive_name, a.archive_type, a.archive_state
FROM 项目主表 p
LEFT JOIN 档案主表 a ON p.project_no = a.project_no
```

用途：从项目看它产生了哪些档案。

### 3.2 合同管理应用内的 2 条

**④ 项目合同汇总查询** —— 从合同反看项目

```sql
SELECT p.project_no, p.project_name,
       COUNT(c.contract_no)     AS contract_count,
       SUM(c.contract_amount)   AS total_amount,
       SUM(c.paid_amount)       AS total_paid
FROM 项目主表 p
LEFT JOIN 合同主表 c ON p.project_no = c.project_no
GROUP BY p.project_no
```

**⑤ 合同付款进度查询** —— 合同主表 × 合同付款表

```sql
SELECT c.contract_no, c.contract_name, c.contract_amount,
       SUM(p.apply_amount) AS pay_total,
       ROUND(SUM(p.apply_amount) * 100.0 / c.contract_amount, 2) AS pay_rate
FROM 合同主表 c
LEFT JOIN 合同付款表 p ON c.contract_no = p.contract_no
GROUP BY c.contract_no
```

用途：`pay_rate` 即付款进度百分比，是合同执行监控的核心指标。

### 3.3 预算管理应用内的 2 条

**⑥ 预算执行汇总查询** —— 预算主表 × 预算明细表

```sql
SELECT b.budget_no, b.budget_name, b.project_no, b.total_amount,
       SUM(d.exec_amount) AS executed,
       ROUND(SUM(d.exec_amount) * 100.0 / b.total_amount, 2) AS exec_rate
FROM 预算主表 b
LEFT JOIN 预算明细表 d ON b.budget_no = d.budget_no
GROUP BY b.budget_no
```

**⑦ 项目预算关联查询** —— 项目主表 × 预算主表（**跨应用**）

```sql
SELECT p.project_no, p.project_name, p.total_budget,
       b.budget_no, b.total_amount, b.executed_amount
FROM 项目主表 p
LEFT JOIN 预算主表 b ON p.project_no = b.project_no
```

### 3.4 财务管理应用内的 3 条

**⑧ 项目成本汇总查询** —— **本方案最重要的跨应用查询**（项目 × 财务）

```sql
SELECT p.project_no, p.project_name, p.total_budget,
       SUM(e.total_amount) AS expense_total,
       SUM(e.total_amount) - p.total_budget AS variance,
       ROUND((SUM(e.total_amount) - p.total_budget) * 100.0 / p.total_budget, 2) AS variance_rate
FROM 项目主表 p
LEFT JOIN 报销主表 e ON p.project_no = e.project_no
GROUP BY p.project_no
```

这条 SQL 把**项目总预算**（来自项目管理应用）与**实际报销发生额**（来自财务管理应用）放在一起做差，直接得出**成本偏差与偏差率**。项目超支与否，一句话看清。

**⑨ 预算执行核查** —— 预算 × 报销（**跨应用**）

```sql
SELECT b.budget_no, b.budget_name,
       b.total_amount AS budget_amount,
       SUM(e.total_amount) AS expense_amount,
       b.total_amount - SUM(e.total_amount) AS remain
FROM 预算主表 b
LEFT JOIN 报销主表 e ON b.budget_no = e.budget_no
GROUP BY b.budget_no
```

用途：预算额度够不够花，`remain` 字段直接给答案。

**⑩ 合同付款核查** —— 合同 × 付款（**跨应用**）

```sql
SELECT c.contract_no, c.contract_name, c.contract_amount,
       SUM(p.payment_amount) AS paid_total
FROM 合同主表 c
LEFT JOIN 付款主表 p ON c.contract_no = p.contract_no
GROUP BY c.contract_no
```

用途：合同签了多少、实付了多少，财务视角交叉核对。

### 3.5 档案管理应用内的 3 条

**⑪ 档案业务关联查询** —— 档案主表 × 档案关联关系表

```sql
SELECT a.archive_no, a.archive_name, a.archive_type, a.source_app,
       l.biz_type, l.biz_no, l.project_no
FROM 档案主表 a
LEFT JOIN 档案关联关系表 l ON a.archive_no = l.archive_no
```

**⑫ 项目全量档案查询** —— 项目 × 档案（**跨应用**）

```sql
SELECT p.project_no, p.project_name,
       a.archive_no, a.archive_name, a.archive_type,
       a.retention_period, a.storage_location
FROM 项目主表 p
LEFT JOIN 档案主表 a ON p.project_no = a.project_no
```

用途：一个项目从立项到结项一共产生了哪些档案，连同保管期限和存放位置一次列清。

**⑬ 档案逾期未归还查询** —— 单表条件查询，支撑借阅管控

```sql
SELECT b.borrow_no, b.archive_no, b.borrower,
       b.borrow_date, b.plan_return_date, b.borrow_status
FROM 档案借阅表 b
WHERE b.borrow_status <> '已归还'
  AND b.plan_return_date < CURRENT_DATE
```

用途：找出所有已过计划归还日但仍未归还的档案借阅记录，供档案管理员催办。

## 五、与 O2OA 系统内已有应用的对接

五个应用不是封闭体系。以下是可对接的切入点和具体做法。

### 5.1 与组织架构（Org）的对接

流程节点的处理人脚本已经在调用 O2OA 组织架构 API：

```javascript
// 取创建人的上级领导
return this.org.listLeaderByIdentity(this.workContext.getWork().creatorIdentityDn, false);

// 按「部门 + 职务」精确定位到具体人员
return this.org.listIdentityWithUnitWithName('财务部', '财务主管');

// 取创建人所在部门（用于部门级审核）
return this.org.listUnitByIdentity(this.workContext.getWork().creatorIdentityDn, true);
```

这意味着**只要维护好组织架构，五大应用的审批链路就自动生效**，不需要逐个流程手工指定审批人。

### 5.2 与人员、身份、群组的对接

应用包的 `availableIdentityList` / `availableUnitList` / `availableGroupList` 三个字段控制应用可见范围，当前为空（表示全员可见）。若要按部门授权，在应用属性的「可见范围」处配置即可。

### 5.3 与内容管理（CMS）的对接

本批应用包暂未包含 CMS 栏目（`cmsList` 为空）。如需发布制度、模板等文档，可：

1. 在内容管理应用中新建栏目（如「项目管理制度」）。
2. 在表单中嵌入 CMS 文档列表组件，或在门户中引用该栏目。

### 5.4 与门户（Portal）的对接

本批应用包未含门户页面（`portalList` 为空）。建议的落地路径是**先用视图和统计功能**：

- 各应用已有 21 个视图和 20 个统计，直接可以挂在门户上做数据卡片。
- 需要综合看板时，新建门户页面，拖入「视图」组件，选择相应的视图（如「项目台账视图」「合同到期预警视图」）。

这样做的原因是：视图和统计是**数据层**能力，先保证数据准确；门户是**展示层**，样式调整频繁，等数据结构稳定后再做门户，返工成本最低。

### 5.5 与已有应用的数据互通

如果系统内已存在其他应用（如办公用品、人事、会议等），互通方式统一是：

1. **确认关联键**：对方应用的自建表里是否有 `project_no`（或其他可对应的编号）。有则直接 JOIN。
2. **新增查询配置**：在需要看数据的那一侧新建查询配置，写 JOIN 语句。
3. **无关联键时**：在流程设计的表单里增加一个关联编号字段，并在流程结束的脚本里写入自建表。

### 5.6 与即时通讯、消息提醒的对接

流程节点的处理人配置完成后，O2OA 会**自动**向处理人推送待办消息到系统内部消息与移动端。若需推送到企业微信/钉钉，需在系统设置的「消息通道」中配置对应通道，无需改动应用包。

## 七、设计取舍说明

以下是本方案中做过的几个关键取舍，供评估时参考。

### 7.1 为什么用自建表而不是只用流程数据表

O2OA 的流程实例数据存在 `Work` / `WorkCompleted` 等表中，用 JSON 存储表单数据。查询单条流程没问题，但**跨流程、跨应用做聚合统计非常不便**。

自建表把关键字段抽出来做成扁平结构，用标准 SQL 查询，性能和便利性都大幅提升。代价是需要在流程流转时把数据写进去（见第八章）。

### 7.2 为什么档案用独立的关系表

一份档案可能同时关联项目 + 合同 + 报销。如果全塞进档案主表，字段会无限膨胀。

拆出 `档案关联关系表`（`archive_no` + `biz_type` + `biz_no`）后，档案与业务的关联变成**多对多**，新增业务类型只需新增一个 `biz_type` 值，不动表结构。这是本方案中扩展性最好的设计。

### 7.3 为什么预计算项目成本汇总表

「项目成本汇总查询」已经能算出成本，为什么还要一张 `项目成本汇总表`？

因为该查询涉及 `LEFT JOIN` + `GROUP BY` + 全表扫描，**数据量大后性能下降明显**。项目看板是高频访问场景，不能每次打开都跑重查询。

做法是：财务流程结束后，用脚本把汇总结果**预先算好写进汇总表**，看板直接读单表。这是典型的**空间换时间**。

### 7.4 金额分级为什么用脚本而不是审批矩阵

O2OA 支持配置审批矩阵，但矩阵配置在界面上是逐条录入的，规则多时维护成本高。

本次对「报销金额 ≥ 5000 走主要领导审批」这类单一阈值场景改用路由条件脚本，一次书写长期生效，且脚本本身可读（就是一句金额比较），后续调整阈值只改一个数字。

## 八、数据写入的实现方式

查询配置解决的是「读」，写入需要在流程结束时执行脚本。以下是推荐写法。

### 8.1 流程结束节点的写入脚本

在流程的**结束节点**或最后一个办理环节的 `afterExecuteScript` 中写：

```javascript
// 以项目立项审批流程为例
var data = this.data.project_base;          // project_base 是表单模块分组名
var work = this.workContext.getWork();

// 通过 SQL 服务写入自建表（O2OA 8.x+ 提供 this.statement 系列 API）
// 具体调用方式请依据你的 O2OA 版本查询「数据服务」文档
```

> **说明**：O2OA 跨版本的数据写入 API 有差异。8.x 之前多用 RESTful 接口调用，8.x 之后提供 `this.statement` 系列。建议在具体版本上先做一个最小验证，确认 API 形态后再批量配置。

### 8.2 一个稳妥的替代方案

如果不想在流程里写复杂脚本，还有一条更简单的路：

1. 流程正常走完，数据存在流程实例中。
2. 用**定时任务**（O2OA 的「定时器」功能）每天跑一次同步脚本，把新完成的流程数据同步进自建表。
3. 自建表只做**读**用途（查询、统计、看板），不做写入源。

这样做的好处是：**流程设计与数据同步解耦**，出问题时互不影响，也便于回溯。缺点是数据有最多一天的延迟。对管理看板类场景，这个延迟通常可接受。

### 8.3 主键生成建议

自建表的 `project_no` / `contract_no` 等业务编号，建议用**业务前缀 + 年份 + 流水号**规则：

```
XM2026001    项目
HT2026001    合同
YS2026001    预算
BX2026001    报销
FK2026001    付款
DA2026001    档案
JY2026001    档案借阅
```

好处是**人读得懂**（看编号知道年份和类型），且天然有序便于排序。缺点是并发下流水号可能冲突，需要加锁或改用时间戳后缀。
