### 关键技术要点（已沉淀为 `zero-dep-xlsx` 技能）
1. .xlsx = zip + XML；字符串用 `inlineStr` 可**完全省掉 sharedStrings.xml**
2. `fills` 索引 0/1 被 Excel 强制占为 `none` / `gray125`，自定义从 2 开始
3. 颜色必须 8 位 ARGB（`FF2B6CB0`），6 位会被当索引色
4. 工作表名 ≤31 字符、不含 `[]:*?/\`、不重名 —— 违反任一条整个文件打不开
5. 非法 XML 字符（控制字符）会让 Excel **静默拒绝**，必须过滤
6. 冻结窗格 `ySplit` / `topLeftCell` / `activePane` 三属性必须配套
7. **PowerShell 输出会被宿主吞掉** —— 让脚本 `Set-Content` 写文件，再用 Read 读
8. 本机 `Excel.Application.Version` 返回 `12.0`，实为 WPS 注册的兼容 ProgID，仍可作真机验证依据

## 第五轮（20 日午后）：★ 门户首页白屏 —— 根因锁定与全量修复

用户反馈：「人力资源和合同管理，首页都是空白」。经查不止这两个，**我们自建的 10 个门户页全部白屏**。

### ★ 根因（决定性证据）
O2OA 门户页 **不是网页，是被当成「表单(Form)」渲染的数据对象**。
`webServer/x_component_portal_Portal/PortalPage.js` 把 `page.data`（`PTL_PAGE.xdata`）
做 `JSON.decode` 后交给 `MWF.APPForm` 渲染。我们原先写入的是**裸 HTML** →
`JSON.decode` 失败 → `this.page` 为 null → `openPortal()` 静默空转 → **整页白屏，服务端零报错**。

实证 SQL（库内原生页 vs 自建页格式对比）：
```sql
SELECT CASE WHEN LEFT(TRIM(xdata),1)='{' THEN 'JSON'
            WHEN LEFT(TRIM(xdata),1)='<' THEN 'HTML' END AS kind, COUNT(*)
FROM PTL_PAGE GROUP BY kind;
-- 原生 94 页：100% JSON；我们 10 页：100% HTML  ← 根因
```

### 原生门户页数据格式（必须照抄）
```json
{"json":{ …表单定义… }, "html":"<div mwftype=\"form\">…模块节点…</div>",
 "id":"", "isNewPage":false}
```
- **Html 模块**（`x_component_process_Xform/Html.js`）用
  `node.insertAdjacentHTML("beforebegin", json.text)` 注入正文；
  注入的是**桌面同一个 document（非 iframe）**；`<script>` **不执行**；`<style>` 生效。
- 因此：**CSS 必须限域**，否则 `body{}`/`*{}` 污染整个 O2OA 桌面。
- **运行时 JS 必须放表单事件**：`Form._loadEvents()` 执行 `json.events.postLoad.code`；
  写在 Html 模块里的 `<script>` 不会跑。
- **表单 DOM 骨架不能缺**：`Form._getModuleNodes()` 靠 `html` 字段里的 `mwftype` 节点定位模块，
  缺骨架则模块拿不到 node。顶层 `html` 需形如
  `<div mwftype="form" id=…><div mwftype="html" id="html"></div></div>`。
- Iframe 模块**不可用于活数据**：只接受 `src` URL，`data:` URL 会变 opaque origin。

## 第六轮（20 日午后后半）：★ 修正第五轮结论 —— 缺了「双层 JSON」这一层

用户浏览器实测仍报错：`o2.decodeJsonString` 抛 `SyntaxError: Unexpected identifier 'json'`。

### ★ 真根因（比第五轮更深一层）
只改成表单定义 JSON 还不够。O2OA 对 data 是**双层约定**：
- 前端固定链：`PortalPage.js` → `JSON.decode(MWF.decodeJsonString(json.data.data))`
- `o2.decodeJsonString(str)` 的实现是把 str **原样拼进** `["…"]` 再 parse
  （o2.js 25896 行）→ **str 本身必须是「JSON 文本再被 JSON 转义一次」的形态**
  （`{\"json\":…}`，即原生 o2.encodeJsonString 的产物）。
- 我们存裸 JSON `{"json":…}` → 拼出 `["{"json":…` → 第一个 `"` 提前闭合 → 报错。

### 库内形态普查（实证）
- `PP_E_FORM` 转义 54 / 未转义 53（53=我们的，全错）；`PTL_PAGE` 转义 94 / 未转义 10。
- **QRY_VIEW / QRY_STAT / QRY_SCH_TABLE / 字典等不经过 decodeJsonString，
  原生存的就是未转义 JSON → 不能一刀切，按实体分别对待。**
- 修复后复核：PTL_PAGE 104/104、PP_E_FORM 107/107 全部转义形态，未转义归零。

### 生成侧修复
- `o2oa_builder.py`：新增 `escape_json_string()`（=o2.encodeJsonString，`json.dumps(s)[1:-1]`）、
  `decode_json_string()`（逆运算）、`is_escaped_json()`；
  `WrapForm.data`（671 行）与 `portal_page.data/mobileData`（1675 行）走 escape。
- 自建表 data/draftData **保持裸 JSON**（建表三连直接读，不转义）。
- 消费方同步：`validate_portal.py`（P0a 验形态+P0b 复刻解码链）、
  `validate_xapp.py`（表单+门户页都验转义形态）、`validate_form_tree.load_design`、
  `preview_portal.py`、`verify_portal_live.py`（R2 完整复刻双层解码）。
- 曾因 validate_xapp 只改了门户页漏了表单 → 8 个表单报"不是合法 JSON"，已补。

### 结果
七道校验全绿 → 导入 15/15 HTTP 200 → 线上 R1~R5 10/10 全绿。
**教训：验证器必须完整复刻前端解码链（双层），少复刻一层就会漏检——
上一轮 verify 全绿但浏览器白屏，正是因为 verify 只做了一次 JSON.decode。**
