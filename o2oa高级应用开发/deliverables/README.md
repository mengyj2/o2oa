> 本目录存放「中国复合材料工业协会」O2OA 实例的**自研应用设计包**，用于源码仓自含应用设计、可重新导入复现。

---

## 一、应用设计的「三种来源」如何统一（核心策略）

历史上存在三种产出 `.xapp` 的方式，彼此冲突。现已**统一到唯一真值形式**：

| 方式 | 做法 | 问题 | 定位 |
|---|---|---|---|
| ① `def_*.py` 按设计生成 | Python 定义结构，硬编码固定 id（`a1001000-...`） | 与 live 脱节（live 用随机 UUID）；且部分域在 live 已改名/合并 | **新建脚手架**（仅创建期使用） |
| ② 按 id 从 live 导出 | 用设计固定 id 去 live 拉数据 | **根本不可行**：live 是随机 UUID，永远对不上，实测 0/7 | **废弃** |
| ③ 按名字从 live 重新导出 | 用 live 应用名拉回完整 Wrap，经 `module/output` 整包下载 | 无（100% 对齐线上） | **★ git 真值（复现主路径）** |

**统一结论**：仓库 `.xapp` 一律采用 **③ 按名字从 live 导出** 的形态，作为 git 真值。其余两种方式不再作为复现载体：

- **`def_*.py` → 降级为「新建脚手架」**：仅当你要从零创建一个**全新**应用时，用它生成初版结构；新建后**必须立即从 live 重新导出覆盖**（因为 live 会赋随机 UUID，def 的固定 id 产物不能进 git）。
- **按 id 导出 → 直接废弃**：live 随机 UUID 与任何固定 id 设计都不可能对齐，不要再尝试。
- **状态备份（MySQL 全库 dump）→ 保持「权威复现」地位**：`.xapp` 只含应用**结构**（表单/流程/查询/门户定义），**不含业务数据、组织、运行态实例**；那些由状态备份覆盖。二者互补，不冲突。

**生命周期（三种方式各司其职，统一在同一链路）**：
```
def_*.py 新建(创建期) → live 运行(运行期) → reexport 按名字固化进 git(结构真值)
                                                              ↘ 状态备份保运行态(权威复现)
```

## 三、重新导出方法

源仓（D:\O2OA）提供脚本（需本机 O2OA 在线 + 管理员令牌）：
- `o2oa高级应用开发/build/reexport_live_apps.py` —— 导出 01~06 五个基础域
- `o2oa高级应用开发/build/reexport_two_extra.py` —— 补充导出 07 费控、08 通用数据中心

均按**名字**从 live 经 `x_program_center/jaxrs/module/output` 整包组包下载，规避门户/流程单应用 500 的坑。
线上有结构性改动后，重跑这两个脚本重新导出并 commit 进 git，即完成「结构真值」更新。
