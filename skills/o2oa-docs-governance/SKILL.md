# 过程文档治理：修订说明 + 有效性台账 + 门禁

> 适用：任何**长期维护、结论会被后续改动推翻**的文档集（本项目为 O2OA 本地化实例的
> `D:/O2OA/docs/`，64 份过程文档）。核心命题：**文档会过期，但读的人不知道** ——
> 治理的目标不是"把文档写对一次"，而是**让"这份文档现在还能不能用"变成可执行的机器事实**。
> 配套技能：`o2oa-runtime-drift-hardening`（运行态与仓库漂移）、`o2oa-ops`（写入类运维）。

---

## 1. 什么时候该用

- 用户说"文档要加修订说明""避免用错""哪份还能用""做文档总结/总索引"；
- **要新写/重写一篇知识库文章**（先看 §9 正文编排六件套，再登记台账）；
- **要把文章发布进 O2OA 知识库**（先看 §10：标题就是幂等键）；
- 发生了**推翻既有结论**的改动（架构换了、机制退役了、服务容器化了），而散落的文档还写着老做法；
- 发现 **AI 助手照着旧文档回答**（RAG 灌库稿里有过期结论时尤其危险 —— 错误答案会被主动复述）；
- 一份看起来还像"可用分支/可用方案"的东西其实已经停更（最容易用错的那类）。

---

## 2. 判定"某个结论是否失效"——四路取证（★ 不要凭印象）

| 路 | 手段 | 例子（本项目实证） |
|---|---|---|
| **A 制品自述** | 被取代的脚本/配置自己会声明废弃 | `o2oa_netlock.sh` 头部 0–40 行明写【已废弃 / 仅手动兜底】，并指出 `entrypoint.sh` 内 iptables 取代它 |
| **B 代码/配置反证** | 在真源里搜"新机制"是否存在 | `entrypoint.sh` grep 到 `iptables -A OUTPUT -j DROP` ⇒ 封网确实已内建 |
| **C 运行态实测** | 直接问活体 | `docker exec ... iptables -L OUTPUT` 有 6 条规则、末条 DROP ⇒ 自愈在位 |
| **D 跨文档引用一致** | 失效结论往往是**批量**散落的 | `grep -rn 关键词 docs/` 一次揪出 15+ 份（含 `kb-synthesis/` 灌库稿） |

> ★ 只做 A/B 就下结论容易漏；**C 是关键**（"配了"≠"生效"）。D 用来确定影响面。
> ★ 反向证据比正面证据有力：本项目用"网盘真实文件与在线文档列表求交为空"来证明数据源隔离，
> 而不是"没调用网盘接口"这种弱证据。

## 3. 修订说明块规范

位置：**H1 之后**（先看到状态，再看到正文）。形态：`markdown 引用块`，包在 HTML 注释标记里以便幂等替换。

```markdown
<!-- doc-rev:begin -->
> **修订说明** ｜ 文档版本 **v1.1** ｜ 状态 **⚠️ 部分失效** ｜ 最近修订 **2026-09-30** ｜ 核对基线 `ai-stack-10.0.2-20260930`（分支 `feature/o2oa-ai-stack`）
> 变更记录：2026-09-30 加修订说明与失效点标注（正文未改）；2026-09-21 初版。
> ⚠️ 失效点：……（逐条，具体到"哪句话不成立、现在是什么"）
> ✅ 仍有效：……（★ 防止读者把整份文档一起丢掉）
> 📌 补注：……（状态仍为有效，但有需要补充的说明）
> 📄 替代 / 续篇：`docs/xxx.md`
> 🗂 全量台账与状态规范：[`DOC-STATUS.md`](DOC-STATUS.md)
<!-- doc-rev:end -->
```

**四态与使用规则（不允许自创第五态）：**

| 状态 | 含义 | 使用规则 |
|---|---|---|
| ✅ 有效 | 与当前运行态一致 | 可照做 |
| ⚠️ 部分失效 | 主体仍有效，含已失效段落 | 先读失效点 + 仍有效，再看正文 |
| ⛔ 已作废 | 整体不可照做 | 只看替代/续篇；正文仅作历史 |
| 📦 存档 | 历史设计/报告 | 本就不作为操作依据 |

**不变式（由脚本强制）：**
- ⚠️ / ⛔ **必须**列失效点；⛔ **必须**给替代文档，且替代路径必须真实存在；
- ✅ **不许**有失效点（有失效点说明它其实是 ⚠️）—— 想补充说明请用 `📌 补注`；
- 文档内写的状态/版本必须等于台账登记值。

★ **只加头部、不改正文**：历史文档正文有史料价值，风险由头部提示兜住。改了正文就失去"当时怎么做"的对照价值。

## 4. 实现骨架（脚本为唯一真源）

```
tools/o2_docs_audit.py
├── REGISTRY              唯一真源：每份文档的 ver/status/changes/stale/keep/repl/note
├── --apply               把 REGISTRY 渲染成修订块写入各文档（幂等）
├── --render              生成 docs/DOC-STATUS.md（人读台账，含规范+统计+四张状态表）
├── --check               反向门禁，非零退出
└── --all                 apply + render + check
```

`--check` 校验六件事：
1. 磁盘上每份过程文档都在 REGISTRY（新增文档必须显式表态，不能悄悄溜过）；
2. REGISTRY 里每份文档都存在于磁盘；
3. 每份文档都有修订块，且块内状态/版本与台账一致；
4. 非 ok 有失效点、void 有替代、ok 无失效点；
5. 所有替代路径真实存在；
6. **台账 `DOC-STATUS.md` 自身与 REGISTRY 同步**（防手改台账，或改了 REGISTRY 忘了 render）。

```bash
python tools/o2_docs_audit.py --apply    # 写入/刷新修订块
python tools/o2_docs_audit.py --render   # 生成台账
python tools/o2_docs_audit.py --check    # 门禁
python tools/o2_docs_audit.py --all      # 三合一
```

**门禁落地**：`.git/hooks` 不受版本控制 ⇒ 必须「模板入库 + 安装脚本落盘」，否则换机器就悄悄失效。
- `tools/git-hooks/pre-commit`（模板，含 `__PYTHON__` 占位符）
- `tools/install_git_hooks.sh`（探测解释器并替换占位符、备份既有非本门禁钩子、chmod +x）
- 钩子逻辑：**只有本次提交触及 `docs/**.md` 才跑**审计，否则静默退出（不打扰常规提交）。

## 5. ★ 两个会破坏文件的坑（都属"看起来对、其实在破坏"）

### 坑 1：H1 正则把 CRLF 的 `\r` 吃进匹配 → 每次运行多攒一个 `\r`

```python
# ✗ 错：re.M 下 `$` 只匹配 `\n` 之前，`.*?` 会把行尾的 `\r` 包进匹配；
#        随后再补一个行尾 ⇒ 每跑一次多一个 \r（实测攒到 5 个，肉眼看不出来）
m = re.search(r"^#\s+.*?$", text, re.M)

# ✓ 对：整行显式排掉 \r 与 \n
m = re.search(r"^#\s+[^\r\n]*", text, re.M)
```

再加一道自愈：`re.sub(r"\r{2,}\n", "\r\n", raw)` —— 顺手修复历史被写坏的文件（正常文档零命中）。

### 坑 2：`str.replace` 二次转换行尾 → 生成 `\r\r\n`

先把块内 `\n` 换成该文件的行尾（`\r\n`），**又**对拼好的整串做一次 `\n → \r\n` ⇒ 变 `\r\r\n`。
**只转一次**，或者只转块、拼好后不再全局处理。

### ★ 幂等验收法（本技能最实用的一条）

> **`--apply` 必须连跑两次，第二次报「0 写入 / N 一致」才算真的幂等。**

只看第一次"写入了 N 份"完全说明不了问题 —— 上面两个坑在第一次运行时表现完全正常。
另外：**每个文件沿用自己原有的行尾**（同一仓里 CRLF/LF 混排是常态，别统一、别翻转）。
验收时用 `git diff --numstat` 看是否**纯插入 0 删除**（整文件重写 = 行尾被翻了）。

## 6. 注解 git 标签：讲清"是什么 + 还能不能用"

命名沿用既有惯例形成族谱，例：`baseline-10.0.2-20260923` / `ai-stack-10.0.2-20260930`。

**标签注解里必须写三件事：**
1. **它是什么**（这一版包含了哪些能力）；
2. **还能不能用**（★ 对"看起来可用其实已停更"的分支，直接写"仅供历史追溯，勿据此部署"，
   并说明落后主线多少提交）；
3. **配套文档的状态**（哪些文档因它而失效、替代是哪份）。

**额外打一个"回滚锚点"**：在重大架构切换的前一个提交上打标签（如"容器化前夜"），
并列出所有因此失效的文档 —— 这样"想退回旧形态"时知道该切哪里、该读什么。

```
git tag -a <name> <commit> -F -      # 用 heredoc 写多行注解
git ls-remote <remote> | grep refs/tags   # 确认远端已有
```

★ 若镜像仓由 **filter-repo 清洗管道**产出：确认管道是 `push --all --tags` 且 `fetch +refs/tags/*`
—— 否则标签只活在本地，镜像里查不到。

## 7. CHANGELOG 的「被推翻的文档结论」台账

里程碑史里最容易漏、也最有价值的一栏。格式：

| 原结论 | 现在 | 受影响文档 |
|---|---|---|
| 「`docker restart` 后必须重跑宿主 `xx.sh`」 | ❌ 作废 —— 封网已由 `entrypoint.sh` 容器内自愈 | 运维总纲 / SOP / …（10+ 份） |
| 「靠宿主看门狗常驻」 | ❌ 作废 —— 已割接为 compose 容器 | `AI栈看门狗…` ⛔、`kb-synthesis/` 3 份 ⛔ |

> 这一栏填的是**读者最容易踩的雷**，不是给自己记流水账。写"改了 A 文件"没用，
> 要写"**哪句话不再是事实了、现在的事实是什么**"。

## 8. 交付清单（照做即可复用）

```
tools/o2_docs_audit.py              # 唯一真源 + apply/render/check
tools/git-hooks/pre-commit          # 门禁模板（含 __PYTHON__ 占位符）
tools/install_git_hooks.sh          # 安装器（探测解释器 + 备份 + chmod）
docs/DOC-STATUS.md                  # 自动生成台账（勿手改）
docs/CHANGELOG.md                   # 里程碑 + 标签对照 + 被推翻的结论
docs/README.md                      # 总索引：阅读顺序 + 纪律 + 状态速览 + 分支/标签对照
<每份过程文档>                        # H1 之后插入修订说明块
```

**收尾自检（全绿才算完成）：**
1. `--apply` 连跑两次 → 第二次「0 写入 / N 一致」；
2. `--check` → PASS；
3. 三项反向测试必须 FAIL（手改台账 / 新增未登记文档 / 摘掉某文档的修订块），还原后 PASS；
4. `git diff --numstat` → 纯插入 0 删除（唯一删除行应来自索引类文档的重写）；
5. 门禁实跑：有 docs 暂存时打印通过，无 docs 暂存时静默。

## 9. 正文编排：交付级文档的「六件套」（2026-10-29 补充）

> 治理只回答"这份还能不能用"，不回答"能不能读得下去"。一篇给**未来的 AI 和真人同时看**的
> 排障文档，若只有一串线性小节，读者必须从头读到尾才知道结论 —— 这是最常见的"内容对但不好用"。
> 下面六件套是实测有效的结构（对照样板：`docs/knowledge_base/o2oa_onlyoffice_ai_loop_guard_20261029.md` v1.1）。

| # | 组件 | 要点 | 反面（写了等于白写） |
|---|---|---|---|
| 1 | **§0 三十秒版** | 四行表：现象 / 根因 / 修法 / 教训；再加一句**阅读路径**（"只想动手→§4；正排障→§1+§2；防再犯→§3+§6"） | 开篇就是"适用场景…"的套话 |
| 2 | **决策树替代线性罗列** | 把"先查什么"写成 ASCII 分支图，并明写**为什么顺序不能颠倒** | 做成"一到十"的平铺小节，读者自己猜先看哪 |
| 3 | **证据总表** | 一行一条「现象 / 实测证据 / 结论归属」，收拢原先散落各节的碎片；**反向证据（A/B 对照）必须有位置** | 证据散在四节，读者要自己拼 |
| 4 | **命令带预期输出** | 每条命令后面写"预期：`NONE(0)`"「预期：4 秒」 | 只给命令，读者不知道跑对了长什么样 |
| 5 | **红线清单（负面清单）** | 单列"千万别做"若干条；排障时人先查负面清单，再查正向步骤 | 只有正向做法（"应该怎么做"），没有"别做什么" |
| 6 | **复盘 2~3 条** | 写"哪一步判断错了、被什么证据拉回来" | 写成"本次完成了 A/B/C"的流水账 |

**三条反模式（都是踩过的）**：
- 同一结论在四个小节各说一遍 —— 读者会以为是新信息，且互相冲突时无法判断哪个是最新；
- 章节按"**我做的顺序**"排，而不是按"**读者判定的顺序**"排；
- 用表格堆细节但不给"这张表回答什么问题"，表越多越难扫。

## 10. 发布进 O2OA 知识库的坑：**标题就是幂等键**

`tools/o2_kb_publish_doc.py` 的幂等判据 = **同分组下标题相同** ⇒ 走 update 复用原 id。

> ★ **改了 H1 标题再发布 ⇒ 匹配不上 ⇒ 新建第二份**，CMS 与网关 RAG 检索层**同时**出现重复条目
> （2026-10-29 实测：重写时标题少了一个"工具"二字，误建 `4dbcd034`，与 `ce5dbf82` 内容重叠，
> 检索 "定因" 会返回两条）。

**正确姿势**：**先把标题定死再发**；重写正文不动 H1。

已误建时按"保留一份"清理（顺序不能反，先 CMS 后检索层）：

```bash
# ① 删 CMS 文档（服务号 token；返回 {"type":"success","data":{"id":...}} 即成功）
DELETE {BASE}/x_cms_assemble_control/jaxrs/document/{dupId}

# ② 删检索层同 id —— 漏这步 RAG 仍会命中孤儿条目
POST {GW}/idx-gateway-doc/delete   {"id": "<dupId>"}

# ③ 两处都复查只剩一份
PUT  {BASE}/x_cms_assemble_control/jaxrs/document/filter/list/1/size/200
      {"categoryIdList":[知识库栏目id],"documentType":"全部","needData":False}
POST {GW}/idx-gateway-doc/list/paging/1/size/10   {"search":"标题关键词"}
```

**★ 两个会让人误判删除失败/成功的接口细节**：

| 现象 | 真相 |
|---|---|
| 单文档 `GET /document/{id}` 返回 200 但看着"空" | 结构是 **`data.data.$document`（两层 data）**，取一层会以为文档是空的 |
| 删除后 `POST /document/list/...` 报 404 | 该路径不存在，用 **`PUT /document/filter/list/{page}/size/{size}`** 复查 |
| 删除成功但检索层还搜得到 | 少做了上面第 ② 步 |
